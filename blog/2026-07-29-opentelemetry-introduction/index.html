OpenTelemetry 可观测性框架系统性介绍

Posted 2026-07-29 12:00 +0800 by ZhangJie ‐ 4 min read

分享:  

背景 #

微服务和云原生架构普及之后，传统的单体监控手段逐渐失效。以前排查问题，看几台机器的 CPU、内存，翻一翻应用日志就能定位；现在一个请求横跨十几个服务，每层都有自己的日志、自己的指标，出问题时单看某一层根本看不出全貌。

于是就有了"可观测性"（Observability）这个概念。它不是某种具体工具，而是一种能力——你能从系统外部，通过它输出的遥测数据，推断出它内部正在发生什么。可观测性的三个支柱（Three Pillars）大家已经比较熟悉：Traces（链路追踪）、Metrics（指标）、Logs（日志）。

但问题来了：三大支柱各有各的实现库、各有各的协议、各有各的后端。你用 Jaeger 做 Tracing、Prometheus 做 Metrics、ELK 做 Logging，三套 SDK 打进业务代码，团队维护成本高得离谱。更致命的是，三套数据之间没有关联——你看一条错误日志，想知道它属于哪个 Trace，做不到。

OpenTelemetry 就是为了解决这个问题而生的。

OpenTelemetry 是什么 #

OpenTelemetry（简称 OTel）是 CNCF 旗下的一个开源可观测性框架，目标是统一遥测数据的采集、生成和导出标准。它不是后端，不是分析平台——它是一个"数据规格+工具集"，让你的应用产出的 Traces、Metrics、Logs 遵循同一套规范，彼此关联，并且可以导出到任意支持 OTLP 协议的后端。

它由两个历史项目合并而来：OpenTracing（专注 Tracing API）和 OpenCensus（Google 开源的 Metrics + Tracing 库）。合并后吸收了双方的设计经验，形成了更完整的体系。

理解 OpenTelemetry，可以从这几个维度切入：

  • 三大信号（Signals）：Traces、Metrics、Logs 以及它们之间的关联模型
  • 架构分层：API → SDK → Collector → Exporter 的数据管线
  • 数据模型：Span、SpanContext、Resource、Instrument 等核心概念
  • 采样与传播：Head Sampling、Tail Sampling、W3C Trace Context 协议
  • 生态定位：它和其他可观测性项目（Prometheus、Jaeger、Fluentd）是什么关系

下面逐一展开。

三大信号（Signals） #

Traces ##

Trace 描述一个请求在分布式系统中的完整生命周期。它由多个 Span 组成，每个 Span 代表一次操作（RPC 调用、DB 查询、函数执行等）。Span 之间通过 parent_span_id 形成树状结构：

Trace (trace_id: abc123)
├── Span A: API Gateway (root)
│   ├── Span B: Auth Service
│   └── Span C: Order Service
│       ├── Span D: DB Query
│       └── Span E: Cache Get

每个 Span 携带的信息：

字段说明
TraceId整条链路的唯一标识
SpanId当前操作唯一标识
ParentSpanId父操作 SpanId，Root Span 为空
Name操作名称，如 POST /order、SELECT * FROM orders
StartTime / EndTime操作的起止时间
Attributes键值对形式的元数据（如 http.method=POST、db.statement=SELECT...）
Events时间点事件（如异常抛出、重试发生）
Status操作结果（OK / Error）
SpanKind角色：CLIENT、SERVER、PRODUCER、CONSUMER、INTERNAL

Metrics ##

Metrics 描述系统在某段时间内的量化状态——请求 QPS、P99 延迟、错误率、内存使用等。OpenTelemetry 的 Metrics 模型兼容 Prometheus，但抽象层次更丰富。

核心概念：

  • Instrument：度量的"工具"，定义一个指标要测量什么。分 Counter（单调递增）、Histogram（分布统计）、UpDownCounter（可增可减）、Gauge（瞬时值）等类型。
  • Measurement：Instrument 产出的具体数值。比如 Counter 的一次 +1。
  • Metric Data Stream：同一 Instrument 按不同属性组合产出的多个时间序列。比如 http_server_duration 按 http.method 和 http.route 分解，每个组合就是一条独立的 stream。
  • View：SDK 侧的概念，允许在不修改 Instrument 的情况下，对输出的 Metrics 做聚合、改名、过滤。这在多团队共享同一 SDK 配置时非常有用。

一个重要的设计决策：OpenTelemetry 的 Metrics 采用 “Delta Temporality” 和 “Cumulative Temporality” 两种时间模式，分别适用于不同后端——Prometheus 用 Cumulative，而 OTLP 原生后端通常用 Delta。Collector 可以在两者间转换，这个特性在实际集成中非常关键。

Logs ##

Logs 是离散的、带时间戳的文本（或结构化）记录。OpenTelemetry 对 Logs 的处理比前两者晚一些，核心思路是：把 Log 当作一种特殊的 Span Event，通过 trace_id 和 span_id 将日志与 Trace 关联。

一个典型的做法是：应用日志框架（如 Log4j、zap）通过 OTel Bridge 自动注入当前 Span 的 Context，让每行日志自动带上 trace_id 和 span_id。这样在 SigNoz 等平台上，看某条 Trace 时就能同时看到关联日志。

信号关联 ##

三大信号之间并非孤立。OpenTelemetry 设计了一个统一的 Resource 模型和 Context 传播机制，让三者天然关联：

  • Trace ↔ Logs：Log 携带 trace_id + span_id
  • Trace ↔ Metrics：Span 可以产生 Metrics（如 http_server_duration 直方图）
  • Metrics ↔ Logs：可以通过 exemplar 机制将某个 Metric 数据点关联到具体 Trace

架构分层 #

从代码到后端，OpenTelemetry 定义了一条清晰的数据管线：

┌────────────────────────────────────────────┐
│ Application Code                           │
│  ├── API (接口层，定义 Instrument 接口)      │
│  ├── SDK (实现层，负责采样、聚合、导出)       │
│  └── Instrumentation (自动/手动埋点库)       │
└──────────────┬─────────────────────────────┘
               │ OTLP (gRPC/HTTP)
┌──────────────▼─────────────────────────────┐
│ OTel Collector (可选)                       │
│  ├── Receivers (接收 OTLP / Jaeger / ...)  │
│  ├── Processors (批处理、过滤、采样、转换)    │
│  ├── Exporters (输出到后端)                  │
│  └── Connectors (连接 Pipelines)            │
└──────────────┬─────────────────────────────┘
               │ OTLP / Prometheus / ...
┌──────────────▼─────────────────────────────┐
│ Backend (Signoz / Jaeger / Prometheus / ..) │
└────────────────────────────────────────────┘

API 与 SDK ##

API 只定义接口，没有任何具体实现。引入 opentelemetry-api 不会产生任何遥测数据，也不会有性能开销。它提供的是 Tracer、Meter、Logger 的抽象定义，你的业务代码只依赖 API。

SDK 是 API 的具体实现。它负责 Span 的创建和生命周期管理、Metrics 的聚合和导出、采样决策等。引入 SDK 之后才会有实际数据产出。

这种 API/SDK 分离是精心设计的：库作者只在代码中依赖 API，应用程序在启动时决定用哪个 SDK（甚至不用），保证了库不会因为依赖 OTel 而对使用者产生侵入。

Instrumentation 库 ##

OpenTelemetry 提供两种埋点方式：

自动埋点（Auto-Instrumentation）：对 Java、Python、Node.js 等主流语言，OTel 提供 Agent，通过字节码注入或 Monkey Patch 自动拦截 HTTP 框架、RPC 框架、数据库驱动等，无需修改业务代码。Java 的一个 JAR 参数就能让 Spring Boot 应用自动产出 Traces。

手动埋点（Manual Instrumentation）：通过 API 在代码中显式创建 Span、记录属性。适合需要精细控制语义的场景：

Span span = tracer.spanBuilder("processOrder")
    .setSpanKind(SpanKind.INTERNAL)
    .startSpan();
try (Scope scope = span.makeCurrent()) {
    span.setAttribute("order.id", orderId);
    // business logic
} catch (Exception e) {
    span.setStatus(StatusCode.ERROR, e.getMessage());
    span.recordException(e);
    throw e;
} finally {
    span.end();
}

实际落地时通常是"自动为主、手动补充"——基础设施（HTTP、gRPC、DB）用自动埋点，核心业务逻辑用手动埋点加语义化属性。

Collector ##

OTel Collector 是可选的中间件，但强烈建议在生产环境部署。它是一个独立的二进制，核心功能：

  • 协议转换：应用可以发 Jaeger Thrift 进来、Prometheus Remote Write 出去
  • 数据处理：批处理（减少网络开销）、属性过滤（脱敏）、Tail Sampling
  • 路由分发：同一份数据可以同时发给多个后端（比如 SigNoz + 自建 Prometheus）
  • 减轻应用负担：将采样、聚合、导出逻辑从应用进程移到 Collector，减少应用开销

Collector 内部由 Pipelines 驱动，每条 Pipeline 串联 Receiver → Processor → Exporter：

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, tail_sampling]
      exporters: [clickhouse, logging]
    metrics:
      receivers: [otlp, prometheus]
      processors: [batch]
      exporters: [prometheusremotewrite]

OTLP 协议 ##

OTLP（OpenTelemetry Protocol）是 OTel 定义的统一数据传输协议，基于 gRPC（端口 4317）或 HTTP（端口 4318）。它取代了之前的 Jaeger、Zipkin、Prometheus 等专属协议，让开发者只需对接一个协议就能通吃所有后端。

OTLP 的最大优势是保持信号的关联关系。Traces、Metrics、Logs 在相同的请求中一起传输，Resource 信息和 Context 在整个过程中保持不变。

采样策略 #

分布式追踪不可能记录所有请求——高流量系统一天上百亿个 Span，全量采集存储成本吃不消。采样是 OTel 设计中的关键一环。

Head Sampling（头部采样） ##

在 Trace 开始时（Root Span 创建时）做采样决策。优点是简单、开销小；缺点是"看不到全貌就做了决策"——一个请求刚开始时看着正常，后来出了错，但采样已经把它丢弃了。

常用策略：

  • 固定比例：采样 10% 的 Trace
  • 速率限制：每秒最多采样 N 个 Trace
  • 基于属性：只采样特定 Service 或特定路径的请求

Tail Sampling（尾部采样） ##

在 Trace 完成后（所有 Span 收集齐了）再做决策。优点是能基于完整信息判断——“出了错的 Trace 全采样，正常的只采 1%"。缺点是 Collector 需要缓存完整的 Trace 数据直到做出决策，内存开销大。

Tail Sampling 只在 Collector 侧执行，SDK 不支持。这是 SigNoz 等平台的一个关键卖点：内置 Tail Sampling 支持，不需要额外部署处理组件。

Context Propagation（上下文传播） #

要让一个请求跨服务形成完整 Trace，必须在服务间传递 Context（TraceId + SpanId + TraceFlags 等）。OTel 支持多种传播方式：

  • W3C Trace Context：W3C 标准，通过 HTTP Header traceparent 传播。目前的事实标准。
  • B3：Zipkin 的传播协议，遗留系统常用。
  • Baggage：W3C 标准，在 Context 基础上携带自定义的键值对数据，跨服务传播。比如把 user-id、tenant-id 带过去，让下游也能使用。

传播机制的关键在于"不丢、不乱”：异步线程、消息队列的生产-消费模式需要显式处理 Context 传递，否则链路就断了。OTel SDK 对这些场景提供了对应的 API。

与其他标准/项目的关系 #

OpenTelemetry 不是要替代 Prometheus、Jaeger 或 Fluentd，而是要成为它们前面的"统一数据采集层"：

项目关系
PrometheusOTel 兼容 Prometheus 指标格式，Collector 支持 Prometheus Receiver 和 Remote Write Exporter
Jaeger / ZipkinOTel 是它们的"下一代"，兼容 Jaeger/Zipkin 协议，可平滑迁移
Fluentd / LogstashOTel 正在扩展 Logs 能力，未来可能成为统一的日志采集代理，但目前 Fluentd 在日志采集中仍是主流
OpenTracing / OpenCensusOTel 的"前身"，已停止维护，所有用户应迁移到 OTel

一个常见的问题是：“我有 Prometheus 了，还要 OTel Metrics 吗？” 答案是：可以用 OTel Collector 的 Prometheus Receiver 采集指标，用 OTLP 统一输出到后端——这让你用一个 Agent 同时处理 Traces、Metrics、Logs，而不用维护多个采集器。

总结 #

OpenTelemetry 的核心价值可以归结为一句话：用一套 API、一种协议、一个 Collector，统一解决可观测性数据的生产、处理和导出。

它是"标准层"而非"产品层"的项目。你无法直接用它可视化数据，它不存储数据，也不会给你发告警。但它定义了一套规范，让上层产品（SigNoz、Grafana、Datadog）可以用统一的方式消费数据，让你可以自由切换后端而不改代码。
