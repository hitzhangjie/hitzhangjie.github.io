当监控数据'说谎'：Split Lock 引发的 CPU 计量失真

Posted 2026-07-24 00:00 +0800 by ZhangJie ‐ 5 min read

分享:  

那次线上告警，除了 CPU 飙高和 IRQ 突增，还观察到另一个更反常的现象：gopsutil 报告的进程单核 CPU 使用率达到了 350%+。

单核，除以了核数的，理论上不可能超过 100%。

这件事困扰了我很久。和 gopsutil 的开发者讨论过，当时我描述了我的timer irq catchup可能导致导致cpu使用率统计出错的想法，see: #1978 VM stealtime>0, process.Percent(0) / cpu.Counts(true) is higher than 100%。 作者后来专门提交了一个commit，将最大单核CPU使用率锁定在了100%，see: [process]: clamp Percent() to prevent values exceeding 100% per CPU 。

[process]: clamp Percent() to prevent values exceeding 100% per CPU In VM environments with steal time or clock skew, CPU jiffies can advance faster than wall-clock time, causing process.Percent() to return values greater than numcpu * 100%. Clamp the result using math.Min, matching the behavior of cpu.calculateBusy().

Fixes #1978

最近梳理我过去的一些笔记，又拿出来整理一遍，并且将尝试复现的代码补全。

gopsutil 是怎么算 CPU 使用率的 ##

我们的 Go 服务里用的是这样一个公式：

单核CPU使用率% = process_cpu_delta / (wall_clock_delta × num_cpus) × 100

三个变量：

  • process_cpu_delta：来自 /proc/[tgid]/stat 的 utime + stime 增量（单位 jiffies，除以 USER_HZ=100 换算为秒）。内核在每个 timer tick 时，如果当前进程正在运行，就给它的 utime 或 stime 计数器加 1。
  • wall_clock_delta：clock_gettime(CLOCK_MONOTONIC) 的增量，墙钟时间，单调递增。
  • num_cpus：/proc/cpuinfo | grep processor | wc -l，VM 内不变。

正常裸金属上，一个单线程程序同一时刻最多跑在一个核上，所以 process_cpu_delta ≤ wall_clock_delta × num_cpus——单核平均永远 ≤ 100%。即使是多线程程序，由于分子是 tgid线程组的总时间，除以cpu核数之后也肯定 ≤ 100%。

ps: 这里说的是"平均单核"。如果进程有 8 个线程跑满 8 个核，procCPU = 800%，perCore = 800% / 8 = 100%，这才是对的。我们线上报的是 perCore = 350%——意味着进程在 1 秒墙钟里积累了 3.5 秒/核的 CPU 时间，物理上不可能。

三个变量，谁在"说谎" ##

正常场景下三者都没问题。出问题那天，母机上发生了两件事：有 split-lock，st 值有波动。时间点对得上。

三个变量逐一排查：

  • num_cpus——VM 不会因为母机 split-lock 就动态改变 CPU 核心数。排除。

  • clock_gettime——CLOCK_MONOTONIC 在 Linux 下通过 vDSO 调用，不经过内核，效率高且可靠。即使在 VM 里，KVM 的 kvm-clock 或 TSC 通过 para-virtualization 保证了单调性和相当好的精度。要说它不准到 3.5 倍的量级，不太可能。排除。

  • process_cpu_delta——这就剩下它了。/proc/[pid]/stat 的 utime/stime 是 guest 内核维护的计数器。要让它"超发"，需要 guest内核的进程记账和墙钟时间脱节。

虚拟化下的时间账本断裂 ##

要理解为什么 guest 内核会"记错账"，得先搞清楚几件事：vCPU 调度、steal time、以及 timer catchup。

vCPU 其实是一个线程 ##

KVM 虚拟化里，guest 的每个 vCPU 对应宿主机上的一个 QEMU 线程。母机调度器决定这个线程什么时候跑、跑多久——guest 内核对此完全无感知。

当母机上另一台 VM 的 split-lock 拖垮了 CPU 资源（详见之前的文章），我们 VM 的 vCPU 线程也跟着遭殃。问题分两层：

  1. 总线上被堵死：锁总线期间，同一个物理 CPU 上的其他核心都没法访存。我们的 vCPU 即使拿到了时间片，也只能在总线上干等着，做不了任何有用功——被调度了但跑不动。
  2. 调度也被拖累：肇事 VM 的 vCPU 被 KVM 反复暂停-唤醒，产生的上下文切换开销挤占了母机 CPU 资源。如果母机 CPU 超额分配，我们的 vCPU 可能真的长时间分不到时间片。

ps: 很多人（包括一开始的我）会把问题归结为"调度器不调度我们"，但实际上主要矛盾在总线锁阻塞访存——vCPU 不是没被调度，是被调度了却没法访问内存。这两者表象类似（都是进程没进展），但根因完全不同。

steal time 的补偿机制 ##

KVM 为每个 vCPU 维护了一个 steal time 计数器。当 vCPU 被 deschedule 时，hypervisor 记录时间点；恢复时，计算间隔并写入 guest 内核的 steal time 字段。guest 内核在 timer interrupt 中读取这个值，将其反映到 /proc/stat 的 steal 列。

正常情况下，这保证了 guest 的 CPU 记账是准确的：

guest_cpu_time = wall_clock - steal_time

但这里有个前提——steal time 的更新必须是及时且准确的。

那为什么还会出错 ##

问题出在 split-lock 引起的调度模式上。

split-lock 不是"长时间停止调度"（那种 steal 会正常累积），而是高频的、短暂的调度抖动：vCPU 被调度 → 遇到总线锁 → 被暂停/等待 → 再调度 → 再遇到总线锁 → … 在这个快速震荡的过程中，steal time 的更新粒度可能跟不上。

KVM 的 steal time 更新本质上是一个异步通知机制：hypervisor 更新共享内存页中的 steal time 值，guest 内核在 timer interrupt 中读取。如果 vCPU 被暂停和恢复的频率远高于 timer interrupt 的频率（通常 250Hz 即每 4ms 一次），就会出现：

  1. vCPU 在两次 timer interrupt 之间被反复暂停-恢复若干次
  2. steal time 只在 interrupt 时才被 guest 内核读取和记账
  3. 但 /proc/[pid]/stat 的进程 CPU 时间，是在每次 interrupt 时，根据"当前进程是否在运行"来更新的
  4. 如果 vCPU 恢复后立即被当前进程占用，interrupt 会把这部分时间记为进程的 user/system 时间——即使这期间有很大一部分其实是 vCPU 被暂停的时间

等一下——vCPU 被暂停期间，guest 内核根本不在执行，timer interrupt 也不触发，按理说不会记账才对。那超发的 jiffies 到底哪来的？

这就涉及 Linux 内核的lost tick compensation（丢失 tick 补偿）机制。

lost tick compensation 是真正的罪魁祸首 ##

当 vCPU 长时间得不到调度，恢复后 guest 内核发现"上次 timer interrupt 到现在已经过了很久"——远远超过正常的 4ms 间隔。内核的 timekeeping 子系统会做时间追赶：注入"丢失的" tick，补上这段时间的账。

ps: 这里的"补偿 tick"就是 atop 看到 IRQ 飙升的那批 timer interrupt——从硬件层面看是 IRQ 积压后集中涌入（IRQ catchup），从内核记账层面看就是 lost tick compensation。同一个东西，两个视角。

关键问题在于：这些补偿 tick 怎么被分配。

正常的 tick 分配逻辑是：tick handler 发生时，看当前进程是谁，就给谁的 utime/stime +1。

补偿 tick 的 handler 也走同一条路径。假设 vCPU 被 deschedule 了时长 D，guest 内核漏掉了 M 次 tick（M = D × HZ）。恢复后这 M 次补偿 tick 集中触发，每次 tick handler 执行时，内核照常问"current 是谁"——如果恰好是我们的目标进程，就给它加 1 个 jiffy。

所以假账不是"把 D 整个加给了进程"，而是：

额外 CPU 时间 = K / HZ = D × (K / M)

其中 K 是 M 次补偿 tick 里目标进程恰好作为 current 的次数。极端情况下 K ≈ M（恢复瞬间目标进程一直跑在 CPU 上），额外 CPU 时间 ≈ D——进程凭空多出了整整 D 秒的 CPU 时间。

  • vCPU 被 deschedule 时，进程 X 正在运行
  • vCPU 恢复后，内核发现时间跳跃，注入 M 次补偿 tick
  • 这 M 次 tick handler 执行期间，进程 X 恰好一直作为 current
  • 进程 X 的 utime/stime 被加了 M 个 jiffy——而这 M 个 jiffy 对应的真实时间段里，vCPU 根本被暂停了

补偿 tick 把"被偷走的时间"错误地计到了进程头上。而且 deschedule 越久、补偿 tick 中目标进程占比越高，虚假 CPU 时间就越大。

ps: 这个假说解释了为什么 atop（分钟级粒度）看不到 >100%——分钟平均后，尖峰被抹平了。母机看子机 CPU 使用率也不超 100%——母机只看 vCPU 线程的实际 CPU 时间，不管 guest 内部怎么记账。

为什么是 350% 这么夸张 ##

350% 相比正常的 100%，偏差了 3.5 倍。下面的简单模型可以说明补偿 tick 是怎么让数字"膨胀"的，但要达到 350% 还需要更极端的条件。

假设测量间隔 1 秒，vCPU 被 deschedule 了 0.5 秒。以常见的 HZ=250 为例，每个 tick 间隔 4ms，0.5 秒对应 125 个周期。vCPU 恢复时，KVM 发现虚拟 LAPIC timer 已超期 125 个周期，于是一次性将这 125 次虚拟 timer interrupt 注入给 guest。guest 内核逐次处理——每次 tick handler 执行时，检查"current 是谁"，给对应进程的 utime/stime +1。

如果这 125 次 tick handler 执行期间，目标进程有 70% 的时间恰好为目标进程，那就相当于 deschedule 时长的 70%（0.35s）被记到了目标进程头上：

  • process_cpu_delta 比真实值多出约 0.35s 的"虚假 CPU 时间"
  • perCore = (真实CPU时间 + 0.35s) / (1s × num_cpus) × 100

对于一个单线程程序（只跑在一个 vCPU 上），如果真实单核使用率是 30%，加上这 0.35s 虚假时间后变成 (0.3s + 0.35s) / 1s = 65%——仍然远不到 350%。

要产生 350% 这种量级，需要满足更极端的条件：

  • deschedule 时间更长：如果 vCPU 被暂停的时间长达数秒，补偿 tick 的累积量会大得多
  • 多 vCPU 叠加：一个多线程程序，多个线程分布在多个 vCPU 上，如果多个 vCPU 同时经历补偿，虚假时间按线程数放大
  • 补偿 tick 全部算给了同一个进程：在最坏情况下，恢复瞬间恰好是我们的进程在运行，所有补偿 tick 全被记到它头上

这些条件叠加起来——比如 4 个 vCPU、每个被暂停 2 秒、补偿 tick 中有 80% 记给我们的进程——虚假 CPU 时间可以达到 4 × 2s × 0.8 = 6.4s，除以 4 核就是单核 160%，已经超 100%。调度抖动越剧烈，数值就越离谱。

前面提到的那次 350% 异常，很可能就是母机 split-lock 最严重的那几十秒内，上述条件同时命中了。

ps: 这里需要强调的是，我并没有在可控环境下尝试复现、验证过这个假说。以下分析基于对内核机制的推理，不是确认结论。除非真的在 VM 里抓到一次 perCore > 100% 的时刻并同时记录内核 trace，否则不能排除其他机制。

复现尝试 ##

最好的验证方法，就是用代码复现：一个程序触发 split-lock，另一个程序用 gopsutil 的方式监控 CPU 使用率，看能不能抓到 >100% 的尖峰。

Split-lock 触发程序（C） ##

在 x86 上，cache line 是 64 字节。分配一个 64 字节对齐的 buffer，在 offset=60 处放一个 uint64_t，它的 8 个字节覆盖 [60, 67]，跨越了 cache line 边界。对这个地址做 lock addq，CPU 必须锁总线才能保证原子性——这就是 split-lock。

// 分配 2 个 cache line，64 字节对齐
char *buf;
posix_memalign((void**)&buf, 64, 128);

// target 位于 buf+60，8 字节覆盖 [60,67]，跨 cache line 边界 (64)
uint64_t *target = (uint64_t *)(buf + 60);

while (running) {
    // x86-64 上编译为 lock xadd/lock add——触发 split-lock
    __atomic_fetch_add(target, 1, __ATOMIC_SEQ_CST);
}

完整代码：splitlock.c

CPU 监控程序（Go） ##

注意：不能使用我上面提及的那个commit之后的版本，因为作者已经注意到这个问题，并将使用率限制了不能超过单核100%。尽管这种做法没有什么实质意义。

复现了 gopsutil 的计算逻辑：

// 读取 /proc/[pid]/stat 的 utime + stime
cpu1 := readProcessCPUSeconds(pid)
t1 := time.Now() // CLOCK_MONOTONIC via vDSO

time.Sleep(interval)

cpu2 := readProcessCPUSeconds(pid)
t2 := time.Now()

procDelta := cpu2 - cpu1
wallDelta := t2.Sub(t1).Seconds()

perCore := procDelta / (wallDelta * float64(numCPUs)) * 100

if perCore > 100.0 {
    log.Printf("⚠️ ANOMALY: per-core CPU = %.2f%%", perCore)
}

Docker vs VM ##

这里有一个重要的限制：Docker 复现不了 350% 的异常。

Docker 容器共享宿主机内核，/proc/stat 和 clock_gettime 都来自同一个内核。没有 guest 内核、没有 steal time、没有 kvm-clock、没有 vCPU 调度、没有 lost tick compensation。split-lock 在 Docker 里只会让系统变慢，但不会导致 CPU 记账失真。

必须用真实的 KVM 虚拟机。完整 QEMU/KVM 复现脚本：vm-setup.sh

复现的基本步骤：

  1. 母机上启动两个 VM
  2. VM-A 中运行 splitlock（触发母机资源争抢）
  3. VM-B 中运行 cpumon（监控 CPU 使用率）
  4. 观察 VM-B 的 cpumon 输出中 PerCore% 是否超过 100%

注意：母机上需要先关闭 split-lock 检测（sysctl -w kernel.split_lock_mitigation=0），否则 guest 内的 splitlock 进程可能收到 SIGBUS。

ps: 即使条件满足，350% 这种极端值也不是每次都能复现。它是一个概率性问题，依赖于母机当时的调度状态和 lost tick compensation 的触发时机。这也解释了为什么当时 atop（分钟粒度）看不到——尖峰只在秒级采样窗口中出现，平均后就没了。

小结 ##

这件事暴露了几个有意思的点：

  • 虚拟化下的监控数据不是绝对可靠的。/proc/stat 的计数器在 guest 里是由 guest 内核维护的，而 guest 内核的"时间认知"和墙钟可能不一致。当母机出问题时，这个不一致会被放大。
  • split-lock 的影响远不止"性能下降"。它通过母机调度 → vCPU 抖动 → lost tick compensation 这条路径，能扭曲 guest 内的 CPU 计量本身。运维如果只看监控数据来做决策，可能完全被误导。
  • “母机调度问题"导致的结果，这个推理是有道理的，只是他没展开解释具体机制。lost tick compensation + steal time 更新延迟 + split-lock 调度抖动，这三者叠在一起才可能产生 350%+ 的异常值。
  • 没在可控环境下复现过，上面的分析仍然只是假说。如果有人有条件在 KVM 环境下跑复现脚本并抓到异常，欢迎反馈。
