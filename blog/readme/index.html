Tick catchup 追踪脚本 #

在 guest 内 看单次 timer IRQ 上：

  1. 补偿了多少个 lost tick（tick_periodic 循环次数）
  2. 有多少次真正记到进程时间（account_user_time / account_system_time）
  3. 有多少次记到 idle（account_idle_time）

catchup 是 guest 内核路径，必须在 guest 跑。

选哪个 ##

Guest 内核脚本
CentOS 7 / 3.10trace-tick-catchup-ftrace.sh
有 bpftrace 的较新内核trace-tick-catchup.bt

字段含义 ##

每次打印一行 CATCHUP：

字段含义
ticks本次 tick_handle_periodic 内 tick_periodic 次数 = 处理的 tick 总数
lost_extraticks - 1，相对「只处理当前这 1 个 IRQ」多补偿的次数
uptupdate_process_times 次数（应 ≈ ticks）
user / sysaccount_user_time / account_system_time：真正往进程 utime/stime 走的次数
idleaccount_idle_time
chargeduser + sys（ftrace 脚本）
est_ms粗算：ticks * 1000 / HZ（默认按 HZ=1000）
current当时 current（仅 bpftrace；catchup 会记到谁头上）

判读：

  • ticks=1：正常 tick，不打印（默认 MIN_TICKS=2）
  • ticks=3000, lost_extra=2999：大约补了 ~3s（HZ=1000）
  • upt ≈ ticks 但 user+sys ≪ ticks：调用了记账入口，但进程没吃满——常见是 idle 或 steal 扣掉（ftrace 会打 note: charged < ticks）

3.10：ftrace ##

mount | grep debugfs || mount -t debugfs none /sys/kernel/debug
chmod +x trace-tick-catchup-ftrace.sh

# 推荐：只看每次补偿明细
taskset -c 1 sudo ./trace-tick-catchup-ftrace.sh catchup

# 每秒总览 + 穿插 CATCHUP 行
taskset -c 1 sudo ./trace-tick-catchup-ftrace.sh stats

# 原始 kprobe + 汇总
taskset -c 1 sudo ./trace-tick-catchup-ftrace.sh stream

# 采 15 秒
taskset -c 1 sudo ./trace-tick-catchup-ftrace.sh count 15

# 只关心更大的补偿（例如至少 10 个 tick）
taskset -c 1 sudo MIN_TICKS=10 ./trace-tick-catchup-ftrace.sh catchup

# HZ 不是 1000 时改 est_ms
taskset -c 1 sudo HZ_ASSUME=100 ./trace-tick-catchup-ftrace.sh catchup

实锤样例（当前 lab：3.10 + highres=off nohz=off） ##

在 guest 内跑 catchup/stream 时，抓到过单次 IRQ 处理 2 个 tick（机制存在；量级为微补偿）：

CATCHUP cpu=0 ticks=2 lost_extra=1 upt=2 user=0 sys=2 idle=0 charged=2 est_ms~2.0

raw 对应（同一次 thp_enter…thp_exit，current=bash）：

bash [000] thp_enter → tp → upt → sys_hit   # tick 1
bash [000]             tp → upt → sys_hit   # tick 2（lost_extra）
bash [000] thp_exit

这证明：当前测试环境里 tick_handle_periodic 会在一次 IRQ 中补偿多次，且每次都会走到 account_*_time。
lost_extra=1 只说明多补了约 1 个 tick（~1ms @ HZ=1000），不等于已复现秒级大 burst 或单核 300% CPU。

其它示例（理想中的深度补偿 / 被 steal 吃掉） ##

CATCHUP cpu=0 ticks=3012 lost_extra=3011 upt=3012 user=3010 sys=2 idle=0 charged=3012 est_ms~3012.0
CATCHUP cpu=0 ticks=500 lost_extra=499 upt=500 user=0 sys=0 idle=0 charged=0 est_ms~500.0
  note: charged(user+sys)=0 < ticks=500  (idle=0; rest may be steal or missing probes)

第二行是「loop 了，但进程时间几乎没加上」——和「有 catchup、CPU% 不破 100%」同构。

确认符号：

grep -E 'tick_handle_periodic|tick_periodic|update_process_times|account_user_time|account_system_time|account_idle_time' /proc/kallsyms
cat /proc/timer_list | grep event_handler

较新内核：bpftrace ##

sudo taskset -c 1 bpftrace trace-tick-catchup.bt

每条 CATCHUP 带 current=comm/pid。Ctrl+C 后有 hist 与累计。

权限 ##

root + debugfs + kprobes。
