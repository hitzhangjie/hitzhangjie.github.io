网络割接：核心路由器的"心脏搭桥手术"

Posted 2025-07-15 00:00 +0800 by ZhangJie ‐ 2 min read

分享:  

网络割接（Network Cutover），简单说就是把正在运行的网络设备、线路或业务从旧系统"割断"，再"接入"到新系统上。

打个比方：给正在行驶的火车换一段铁轨——先让火车减速或短暂停下，快速换好，再恢复正常行驶。对核心路由器做割接，就是网络运维里风险最高的一类操作，堪称"网络世界的心脏搭桥手术"。

英文里最专业、最常用的对应术语就是 Network Cutover。其他相关说法有 Network Migration（侧重整个迁移过程）、System Upgrade（目的，不是动作本身）、Planned Network Maintenance（更宽泛的说法，割接是其中一种）。

下面以核心路由器的割接为例，拆解整个流程。

核心理念 ##

动手之前，先搞清楚三条底线：

  • 万无一失：核心路由器是网络骨干，长时间中断意味着大面积瘫痪，没有试错空间。
  • 影响最小化：所有操作的目标是把业务中断时间压缩到秒级甚至毫秒级。
  • 随时可回退：任何一步出错，必须在几分钟内恢复到割接前的状态。

这三条决定了割接不是"上去改一下配置"这么简单，而是一套严密的工程流程。

阶段一：割接前——准备与规划 ##

准备阶段花的时间最长，也最重要。准备越充分，割接窗口里的操作越顺利。

1. 制定 MOP（Method of Procedure） ##

MOP 是割接的"剧本"，精确到每一条命令、每一个端口、每一个负责人、每一个时间点。它不是大纲，是指令集——执行者拿到手就能照着敲，不需要临场判断。

2. 技术勘察 ##

分两层：

  • 物理层：机房空间够不够、电源接口对不对、光纤类型和长度匹不匹配、端口型号兼不兼容。这些看起来琐碎，但任何一项出问题都会让割接窗口直接报废。
  • 逻辑层：梳理这台路由器连接了哪些设备、承载了哪些业务（专线、互联网出口等）、跑了哪些路由协议（BGP、OSPF、IS-IS）和策略。漏掉任何一条，割接后可能就是业务断连。

3. 准备新设备 / 配置 ##

如果是换硬件，新设备先在 Lab 环境里完成完整配置和测试，模拟生产环境的流量和协议行为。不要相信"配置一样直接上线就行"，生产环境的 corner case 只有跑过才知道。

如果是软件升级或配置变更，新的配置文件必须提前写好、经过 Peer Review，并且做语法检查。

4. 备份 ##

  • 备份当前 running-config
  • 备份 License（如果有的话）

这一步不花多少时间，但救命的概率不低。

5. 采集基线数据 ##

割接前记录下网络"健康"状态，作为割接后对比的依据：

show ip route          # 路由表
show bgp summary       # BGP 邻居状态
show interfaces        # 接口状态和流量
show ip traffic        # IP 流量统计

还要记录设备的 CPU、内存使用率，以及 ping、traceroute 关键业务地址的延迟。

6. 制定回退计划 ##

回退方案必须和执行方案一样详细——在哪个步骤出错时，依次执行哪些命令来撤销变更。不要写"如果出问题就回退"，要写"在步骤 N 失败时，执行命令 A、B、C，预期恢复到状态 X"。

7. 沟通与通知 ##

  • 确定割接窗口：选业务量最低的时段，通常是周日凌晨 2:00–4:00。
  • 通知相关方：受影响的部门、客户、NOC（网络监控中心），告知时间、目的、潜在影响。
  • 组建团队：明确分工——总指挥、命令执行人、物理操作人、验证人、对外沟通人。割接期间通常会建一个专门的电话会议或 IM 群组。

阶段二：割接中——精确执行 ##

割接窗口一开，时间紧、压力大，严格按 MOP 执行是唯一的路。

1. 开始前最终检查 ##

窗口开启时，先确认网络状态平稳、没有突发告警。然后在团队频道里宣布：“割接正式开始。"——这句话意味着所有人进入按剧本执行的状态。

2. 流量切换（优雅排干） ##

直接 shutdown 接口是最粗暴的做法，正确的方式是利用路由协议让流量平滑地切换到备用路径：

  • 调整路由 metric：逐步调高当前路由器的 OSPF cost 或增加 BGP AS-PATH，让网络中的其他路由器"主动"避开这台设备，流量自然排干。
  • 关闭 BGP 会话：shutdown BGP 邻居关系，让流量从其他出口走。

等流量降为零，才可以进行物理或配置变更。

3. 执行核心变更 ##

根据割接类型执行：

  • 软件升级：执行升级命令，重启设备。
  • 硬件更换：确认流量为零后，shutdown 接口，拔光纤，连到新设备，no shutdown 新设备接口。
  • 配置变更：加载新的配置文件。

4. 流量恢复 ##

把之前调整的路由协议参数恢复正常值，让流量"流回"到新设备上。

5. 立即验证 ##

每执行完一步关键操作，立刻验证：

show interfaces              # 接口是否 up/up
show ip ospf neighbor        # OSPF 邻居是否建立
show bgp summary             # BGP 邻居状态
show ip route                # 路由表是否按预期学习
ping <target>                # 连通性测试

阶段三：割接后——监控与确认 ##

操作完成不等于收工，持续监控和最终确认同样关键。

1. 深度监控 ##

把当前设备的 CPU、内存、流量、延迟与割接前的基线数据逐项对比。同时观察日志，看有没有异常报错、接口 CRC 错误或 flapping。

联系业务方或用自动化探针确认关键业务（数据库连接、应用访问）正常。

2. 宣布割接成功 ##

监控期通常 30 分钟到 2 小时。一切平稳后，总指挥宣布：“割接成功，进入监控期。”

3. 清理工作 ##

  • 确认新设备稳定运行一段时间（可能是几天）后，再下电、下架旧设备。
  • 移除割接过程中使用的临时路由策略。

4. 更新文档 ##

  • 更新网络拓扑图
  • 更新 CMDB（设备信息库）
  • 归档 MOP 和操作记录

5. 复盘总结 ##

召开复盘会议，总结成功经验和不足之处。不是走过场——这次踩的坑，要让它变成下次 MOP 里的检查项。

总结 ##

网络割接的核心不是技术难度，而是工程纪律。三个阶段的每一环都有明确的检查和验证，目的就是在变更不可避免时，把风险控制在可预见的范围内。MOP 写得越细、准备越充分、回退路径越清晰，割接窗口里的压力就越小。

ps: 实际割接中还有很多细节因环境而异——比如是否涉及 MPLS、VRF、多厂商设备混跑等场景，这里不过多展开了。
