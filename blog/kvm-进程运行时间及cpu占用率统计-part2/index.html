kvm(5)：vDSO 时钟失真导致分母偏小，CPU% 虚高的另一种可能

Posted 2026-07-30 12:00 +0800 by ZhangJie ‐ 2 min read

分享:  

前几节的推演都围绕着分子偏大这条思路——tick catchup、steal time 未同步、两点采样时序错位，都是试图解释 Δ(utime + stime) 的异常膨胀。但换个角度想：CPU% = Δcputime / (ΔT × N) 这个公式里，分母 ΔT 出问题也能导致同样的结果。

这里我们就来讨论CPU虚高的另一种可能，vDSO 时钟失真导致分母（ΔT）偏小。

1 分子和分母是两条完全独立的时钟链 ##

在 Go 程序的监控代码里：

  • 分子 Δ(utime + stime)：来自 /proc/self/stat，由内核 tick / 调度器在 task_struct 上硬记账，基于 jiffies，走的是 Host 侧物理时钟 → KVM timer 注入 → Guest 内核记账 这条链
  • 分母 ΔT：来自 Go 的 time.Now()，走 vDSO（pvclock）用户态快速路径，完全不经过内核 syscall

正常场景下两者应当反映同一个物理时间流逝。但在虚拟化环境中，这两条链完全解耦——Split Lock 可能只击穿了其中一条。如果分母 ΔT 被严重压缩（Go 以为只过了 0.1s，物理世界实际过了 1s），即使分子完全正常，计算结果也能达到数倍于 100%。

2 vDSO（pvclock）的时间是怎么算的 ##

在 KVM 子机中，clock_gettime()（Go time.Now() 的底层调用）通常走 pvclock 路径。pvclock 页由 KVM 维护在 guest 物理内存中，用户态通过 vDSO 映射直接读取：

time = system_time + (rdtsc() - tsc_timestamp) × tsc_to_system_mul >> tsc_shift
字段写入者含义
system_timeKVMwall clock 基值，反映 Host 侧物理时间
tsc_timestampKVM与上述system_time 对应的 TSC 快照
tsc_to_system_mul / tsc_shiftKVMTSC 频率到纳秒的换算系数
rdtsc()CPU 硬件当前 TSC 计数器值，随 CPU 运行持续递增

这里的关键是：rdtsc() 是硬件计数器，Split Lock 再严重它也在走。如果两次 time.Now() 读的是同一版本的 pvclock 页，(rdtsc₂ - rdtsc₁) × mul >> shift 一定如实反映 TSC 增量，误差最多 ppm 级（TSC 频率漂移）。40 倍的扭曲不可能出在这个路径上。

但如果两次 time.Now() 之间，KVM 更新了 pvclock 页，且写入的 system_time 是一个偏旧的值，情况就完全不同了。

3 Host 端冻结 → pvclock 基值偏旧 ##

Split Lock 锁死内存总线后，Host 侧的 timer interrupt 无法按时投递到物理核，Host 内核的 timekeeper 停止更新。当 Split Lock 结束、vCPU 恢复调度时，KVM 重新计算 pvclock 页：

  1. KVM 在 VM Entry 时调用 kvm_get_walltime_and_clockread() 读取 Host wall clock
  2. Host timekeeper 刚从冻结中恢复，只补回了一个 tick 的量，并未一次性补齐丢失的全部时间（内核 timekeeping 是逐 tick 追赶的，不是一次性跳变到位）
  3. KVM 用这个偏旧值更新 pvclock 页的 system_time，同时将当前硬件 TSC 值写入 tsc_timestamp

这里有一个容易忽略的细节：tsc_timestamp 是从硬件 TSC 读取的当前值，这意味着它被"重置"到了写入时刻。紧接着 time.Now() 再读 rdtsc() 时，(rdtsc() - tsc_timestamp) 只差了微秒级——TSC 修正项还没有机会累积，所以 time.Now() 返回的几乎就是 system_time 本身。

这就是 pvclock 机制的关键约束：每次 KVM 写入新页，TSC 修正项就从零开始。system_time 承担了基值角色，基值错了，短期内 TSC 修正项帮不上任何忙。当然，这个错误不会持久——等 Host timer tick 恢复、timekeeper 追上真实时间后，KVM 下一次更新 pvclock 页就会写入正确的 system_time，子机的 time.Now() 也随之恢复正常。但监控采样恰好打在偏旧窗口内的话，当次采样算出的 ΔT 就已经被压缩了。

结果：新的 system_time 比真实物理时间落后了一大截。而这是 vDSO 公式里的基值——基值偏小，后续 TSC 增量再正确也算不出对的时间。

4 两次 time.Now() 读到不同版本 ##

场景推演：

t1 = time.Now()
→ pvclock 页版本 V1
→ system_time₁ = S1  （反映大致的真实物理时间）

         ... Split Lock 发生，vCPU 被强占 ...

t2 = time.Now()
→ pvclock 页版本 V2 （KVM 在 VM Entry 时更新了）
→ system_time₂ = S2  （比真实物理时间落后 ~0.9s）

即使中间 vCPU 停摆了 1 秒，TSC 差值如实记录了这段时间，但因为 system_time 从 S1 到 S2 的前进量远小于真实物理时间流逝，t2 - t1 就被严重压缩——监控程序以为只采样了 0.1s，实际上物理世界已经过了 1s。

5 触发条件：三重叠加 ##

这需要三个环节在物理时间轴上恰好对齐：

层级条件Split Lock 场景下
物理层Split Lock 击穿内存总线，cache coherency 停滞AMD EPYC 的 Infinity Fabric 跨 CCD 放大影响面，持续百毫秒甚至秒级
Host 内核层timer interrupt 被持续压制，timekeeper 停止更新恢复后逐 tick 追赶，不一次性补齐丢失的全部时间
用户态读取time.Now() 恰好在 pvclock 页仍偏旧的窗口内执行窗口极窄（微秒级别），但一旦命中，ΔT 显著缩小

三者必须恰好对齐——这也是为什么实验室常规压力测试下极难稳定复现。它不是一个逻辑必然的 Bug，更像是极端条件下的"概率性击中"。

6 能解释什么、不能解释什么 ##

能解释的：

  • 即使"归一化后"（除以 32 核）依然高达 358%——分母被压缩，任何正常的分子都被放大
  • 为什么同一母机上其他 VM 的 CPU 占用率也同步飙升（大家共享 Host timer 状态，都可能读到偏旧的 pvclock 基值）
  • 为什么迁走 Split Lock 源后问题立即消失
  • 为什么在实验室用常规压测手段无法复现

不能 100% 确定的：

  • 没有问题现场的 pvclock 页 dump 和 Host timer 快照，无法直接证明 system_time 确实发生了跳变
  • 无法排除"分子偏大"和"分母偏小"同时发生——两者并不互斥，可能各自贡献了一部分
  • AMD EPYC + 内核 5.4 这一具体组合下 timekeeping 的 tick 补偿行为，没有条件做精确的硬件级验证

7 小结 ##

本节从分母（ΔT）的角度提出了另一种可能：Split Lock → Host timekeeper 冻结 → KVM 写入偏旧的 pvclock system_time → vDSO 返回偏小的 ΔT → CPU% 虚高。

它和前几节讨论的分子偏大路径并不互斥，在 Split Lock 的极端场景下也可能同时作用。但必须强调：以上是结合内核源码和间接证据的技术推演，并未在出问题的那台母机上通过精确 trace 完成 100% 的闭环验证。Split Lock 的极端破坏力让我们在排查中看到了大量异常现象，但要精确归因到具体的内核代码路径，还需要更完善的线上可观测性基础设施，当然也要有现场能稳定或者高概率复现。

这个问题从有限线索推理到现在，目前当前这篇文章，可能离真实原因更加接近，至少从解释释疑的角度来说，是说的通的。OK，就这样，适可而止吧！如果后续再遇到类似现象，可以结合现场再看下。
