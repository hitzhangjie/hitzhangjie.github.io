Split Lock → CPU 计量失真：lab 脚手架 #

配套博客系列（读系列再跑脚本，否则容易踩路径/预期坑）：

篇内容确定性
1 · Split Lock 压垮母机邻机总线锁拖垮母机已认
2 · 监控数据说谎gopsutil 单核 350%、假说现象真；350% 因果未证
3 · KVM 只注 1 个 timerKVM只注 1 个 timer IRQ；periodic loop 才多记机制允许 >100%
4 · Tick catchup 实验ftrace 坐实 catchup；稳定 300% 未复现catchup ✓ · 300% ✗

待验证的假说 ##

假说1：Timer IRQ catchup ##

最开始，受AI影响，我以为会kvm会给子机（guest）连续注入多个丢失的Timer IRQ，后面进一步确定了是注入1个Timer IRQ。后面了解到子机内核接收到Timer IRQ后会补偿进程运行时间，可能是补偿一次（oneshot）或者为missed timer ticks逐个补偿一次。我以为可能是多次补偿导致CPU使用率上升、同时steal time=0（为了方便超卖，云服务商kvm未将实际steal time同步给子机）。

确实可能会超过100%，但是可能达不到300%，下面是我的测试结果，以及后续对线上环境内核、配置的再次印证，确认了这点，几乎不可能是这个假说导致的。

  1. 3.10 + highres=off + nohz=off，handler 为 tick_handle_periodic 时，一次 timer IRQ 内可处理多个 tick（ftrace 抓到过 ticks=2）。

  2. 单核 CPU% 高达 300% 尚未打出；略 >100% 能够复现。不要把本仓库当成「一跑就 350%」的演示。

  3. KVM 不会连灌 N 个 timer IRQ（pending 压成 1）；N 次记账来自 guest 软件 loop。早期文档/笔记里如果提及「注入多个timer IRQ给子机」的说法，是错误描述。

  4. ⚠️ Timer tick catchup 补偿进程过多CPU使用时间，这个假说需要重新审视（2026-07-28）：

    • 线上内核是 5.1 + oneshot + hrtimer_interrupt 模式，不走 tick_handle_periodic 路径；
    • 即使 periodic 下实测补偿量也只有 lost_extra=1（2 个 tick），远撑不起 300%；
    • timer tick 方向可能整体推测错了。

假说2：网络中断积压瞬时涌入 ##

基于上述，线上 5.1 内核走 oneshot 模式，timer tick 补偿路径，说不通。更可能的机制是网卡相关的中断注入导致的。真实线上环境，子机中部署的是一些网络IO密集型服务。延迟调度一小会，可能就会积压大量的网卡中断请求？其实也不会注入大量中断请求。

kvm会采取 Interrupt Coalescing (中断合并) / NAPI Poll (轮询驱动) 的方式来进行处理，当子机被调度那一瞬间，子机内核只能发现有一个网卡中断标志位，然后它可能会去处理这个中断请求，或者说NAPI那样关掉中断去polling去处理 …… 但是kvm绝对不会注入大量的原始网卡中断给子机，因为这会引发 中断风暴（Interrupt Storm）。

那么这条假说，其实也是解释不通的？未必。

硬中断次数可能不高，因为从头到尾只触发了一两次硬中断（cat /proc/interrupts）。但是这次网卡积压数据多、任务量大啊。在 子机醒来的那一刻，CPU 绝大部分时间都耗费在了执行 NAPI 轮询逻辑、从内存拷贝数据包、以及运行高并发网络服务的内核协议栈上（特别是 **NET_RX 软中断，耗时久还会转给ksoftirqd处理）…… 这些会算在 软中断 or 内核态 的统计中，在atop中的CPU使用率中的irq 或者 sys字段中体现。

快速开始 ##

1. 本地编译运行（不触发 split-lock） ##

make all                                 # 编译所有程序
./splitlock 2 &                          # 后台启动 split-lock（2 线程）
./cpumon $(pgrep splitlock)              # 监控其 CPU 使用率
# 或使用 memstress 模拟业务负载
./memstress -t 4 -m random -d 60s &      # 4 线程随机访存，60 秒
./cpumon $(pgrep memstress)

在裸机/Docker 上，PerCore% 始终 ≤ 100%，这是正常基线。

2. Docker 运行 ##

Docker 共享宿主机内核，没有 vCPU 调度和 steal time 机制，无法复现 350% 异常。

3. QEMU/KVM（唯一值得认真打的路径） ##

需要真实 guest 内核 + vCPU 调度 +（可选）steal 暴露开关。Docker/裸机只能做基线。

Guest 硬条件（打 catchup 用）：

# 内核 cmdline（3.10 上逼出 tick_handle_periodic）
highres=off nohz=off

# 进 guest 后确认
cat /proc/timer_list | grep event_handler
# 目标：tick_handle_periodic
# 若是 hrtimer_interrupt：进程只记 1 tick，别指望数倍 %

# 准备 / 启动（细节以 vm-setup.sh 为准）
./vm-setup.sh setup
./vm-setup.sh launch

# VM-A：split-lock 压力（母机需按环境处理 split_lock_mitigation）
# VM-B：memstress + cpumon；或单 VM + 人为拖 vCPU

# 验证 catchup 机制（优先于盯百分比）
# 见 trace/trace-tick-catchup-ftrace.sh 与系列第 4 篇

预期结果（与 lab 对齐） ##

环境预期

要冲「破 100% / 冲数倍」时，优先核对：

#条件说明
1guest 走periodichighres=off nohz=off + event_handler=tick_handle_periodic

3steal 对照开/关-kvm-steal-time，看 raw Δproc vs Δsteal（系列第 4 篇「下一刀」）

关于 “split_lock_mitigation not available” 提示：如果 guest 内核版本较老（如 RHEL 8 的 4.18），没有 split-lock 检测功能，splitlock 程序会打印此提示。这不影响测试 — split lock 在 CPU 硬件层面仍然会发生（lock 前缀指令跨 cache line 时总线必然被锁），且 guest 内核不会 SIGBUS 终止进程，splitlock 可以持续运行。

关于 dmesg 看不到 split lock 日志：split lock 与 split lock 检测是两个独立的概念：

  • Split lock 本身：lock 前缀指令访问跨 cache line 地址时，CPU 必须锁住内存总线才能保证原子性，这是 x86 硬件行为，无法关闭
  • Split lock 检测：通过 MSR 配置让 CPU 在 split lock 发生时产生 #AC 异常，内核捕获后记录日志或发 SIGBUS。这需要 CPU 暴露 split_lock_detect feature bit

在 WSL2 / Hyper-V 环境中，宿主 Hyper-V 不向 WSL2 暴露 split_lock_detect CPUID bit，因此即使 split_lock_mitigate=1，内核也无法捕获 split lock 事件，dmesg 中不会有日志。但总线锁仍然在硬件层面发生，对母机资源争抢的影响依然存在。

关于 350%： 线上尖峰与机制相容，但 lab 尚未稳定打出。分钟级 atop 也容易把秒级尖峰平均掉。细节与失败手段见系列第 4 篇。

Steal 与 catchup（修正版） ##

关键纠正：KVM 只注入 1 个 timer 中断；guest 在 periodic 路径上 loop 多次 tick_periodic，才可能给 current 多记。steal 在每次 account_process_tick 里扣——扣干净则 ftrace 上 catchup 很热闹、/proc 进程 jiffies 却不怎么炸。

场景stealperiodic catchup常见现象
lab 默认开 stealhost 写入 run_delayloop 多次可能tp/thp>1，% 仍贴 100%
关 steal 暴露-kvm-steal-timeguest 侧常为 0loop 多次更值得盯 raw Δproc/Δwall（待验证）
NOHZ + hrtimer guest任意进程只记 1 tick不宜期待数倍 %
PerCore% = proc_delta / (wall_delta × num_cpus) × 100

复现条件分析 ##

在实际测试中发现了两个影响复现的关键因素，记录如下。

因素一：vCPU 超分必须是"真实的" ##

现象：将 -smp 2 改为 -smp 16 后，PerCore% 不再破 100%，甚至连异常波动都消失了。

根因：splitlock 程序默认只启动 2 个线程（./splitlock 2），2 个线程做 split lock 最多只能阻塞 2 个物理核上的内存总线。VM-B 有 16 个 vCPU 时，其余 14 个 vCPU 完全不受影响，正常跑满 CPU——异常被稀释到不可见：

splitlock 线程数 = 2 → 只锁 2 个物理核的 bus
VM-B 16 个 vCPU 中最多 2 个被阻塞
PerCore% ≈ (14×100% + 2×受影响的%) / 16 ≈ 正常值

解决：

  1. splitlock 线程数应 ≥ host 物理核数（./splitlock $(nproc)），确保所有核都被 bus lock 覆盖
  2. 必须做 CPU pinning，把所有 vCPU 线程钉到同一组物理核上。不做 pinning 时，KVM 调度器会在物理核之间迁移 vCPU 线程，splitlock 的线程和 target VM 的 vCPU 可能不在同一组物理核上，bus lock 的影响无法传导：
# 将所有 QEMU vCPU 线程钉到 host 的 0-7 号核
pgrep -f qemu-system | xargs -r taskset -cp 0-3

CPU pinning 还有一个关键作用：即使 splitlock 覆盖了所有核，如果不做 pinning，splitlock 线程和 target vCPU 线程可能被调度到不同的 socket 或 NUMA 节点上（如果 host 有 32 核，两个 VM 的 vCPU 线程可能被分散到不同物理区域），此时 splitlock 锁住的 memory bus 和 target vCPU 所在的 memory bus 不是同一条，target vCPU 仍然不受影响。

因素二：Guest tick 路径（比发行版名更关键） ##

现象：默认 highres 的 3.10 guest、或现代 NOHZ guest，拖 vCPU 也打不出「一次 handler 多记」。

根因：KVM 只递 1 个 timer IRQ。是否给进程记 N 次，看 guest handler：

hrtimer / tick_sched_timer（默认 highres）
  → jiffies 可一次跳 N
  → update_process_times 通常只 1 次
  → 进程账不易按 missed 次数灌

tick_handle_periodic（需 highres=off nohz=off 等）
  → 同一次进入里 for 循环多次 tick_periodic
  → 每次都可能 account_process_tick(current)
  → 机制上可 >100%；量级还看 steal / 采样窗（lab 尚未稳定 300%）

验证：

cat /proc/timer_list | grep event_handler
zgrep -E 'CONFIG_NO_HZ|CONFIG_HIGH_RES_TIMERS|CONFIG_HZ=' /proc/config.gz 2>/dev/null
# 或：grep ... /boot/config-$(uname -r)
发行版内核备注lab 现状
CentOS 73.10可强制 periodic；highres=off nohz=offcatchup 已坐实；稳定 300% 未出
CentOS 8 / 4.18较新默认更易走 hrtimer/NOHZ早期未打出预期尖峰
现代 5.x/6.xGEN 记账等进程侧更不易被 tick 灌爆不宜当 350% 复现目标

真要打 KVM 路径：Linux host + QEMU/KVM + 3.10 guest。WSL2/Hyper-V 的时间与 steal 路径不同，不能直接当对照。

打 catchup / 冲 % 的最小清单 ##

1. Guest: highres=off nohz=off，确认 event_handler=tick_handle_periodic
2. 监控与业务绑不同逻辑 CPU；避免整 QEMU SIGSTOP（墙钟一起冻）
3. 对照实验: 开/关 -cpu host,-kvm-steal-time，打 raw jiffies 而非只看 %
4. 可选: split-lock + pinning 造母机争抢（与「人为拖单 vCPU」二选一或叠加）
5. ftrace: 先证明 one IRQ multiple ticks，再谈 300%

目标分层：机制（catchup） 与 量级（300%） 分开验收。前者 lab 已有；后者仍 open。

cpumon 输出的关键字段：

字段含义正常范围

Appendix #

为什么 Docker 复现不了 ##

┌─────────────────────────────────────────┐
│ Docker Container                        │
│  ├── splitlock (C)                      │
│  ├── cpumon (Go)                        │
│  └── /proc/stat ← 这是 HOST 的 /proc!   │
│      没有 steal time 字段实际值           │
│      没有 vCPU 调度                       │
│      没有 kvm-clock                       │
└─────────────────────────────────────────┘
             │
    ┌────────┴────────┐
    │  Host Kernel    │ ← 共享内核，无 VM 层
    └─────────────────┘

┌────────────────┐  ┌────────────────┐
│ VM-A           │  │ VM-B           │
│ ┌────────────┐ │  │ ┌────────────┐ │
│ │ splitlock  │ │  │ │ cpumon     │ │
│ │ (C program)│ │  │ │ (Go)       │ │
│ └────────────┘ │  │ └────────────┘ │
│       │        │  │       │        │
│  guest kernel  │  │  guest kernel  │
│       │        │  │       │        │
│   /proc/stat ← │  │   /proc/stat   │
│   独立记账     │  │   含 steal time │
└───────┬────────┘  └───────┬────────┘
        │                   │
   ┌────┴───────────────────┴────┐
   │  QEMU/KVM + Host Kernel     │
   │  vCPU 线程调度               │
   │  steal time 更新             │
   │  时间补偿 (timer catchup)    │
   └─────────────────────────────┘

关键差异：VM 有 guest kernel 自己的 /proc/stat 记账 + hypervisor 的 steal time 注入 + vCPU 调度导致的 timer catchup。Docker 三者都没有。
