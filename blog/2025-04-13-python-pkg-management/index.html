Python 项目依赖管理：工具选型与最佳实践

Posted 2025-04-13 00:00 +0800 by ZhangJie ‐ 3 min read

分享:  

问题 ##

Python 的依赖管理工具太多了。

刚接触 Python 的人大概率会遇到这种情况：克隆一个项目，pip install -r requirements.txt，然后发现装不上——缺系统库、Python 版本不对、依赖冲突。折腾半天终于装好了，跑起来报 ModuleNotFoundError，因为全局环境和另一个项目搅在了一起。

这不是新人的问题。Python 的打包和依赖管理经历了漫长的碎片化演进，同一个需求有多个工具在竞争，每个工具的文档都在讲"用我就对了"，但很少有人说清楚"什么场景该用哪个"。

本文把我实际用过的工具和组合整理出来，给不同项目类型一个明确的推荐。

虚拟环境：先隔离再说 ##

第一步必须做的是隔离。每个项目要有自己独立的 Python 环境，不然依赖之间早晚打架。

venv（Python 3.3+ 内置） ##

如果你只需要隔离依赖，venv 够用了。它是 Python 自带的，不需要额外安装。

python -m venv .venv
source .venv/bin/activate   # Linux/macOS
.venv\Scripts\activate      # Windows

优点是没有外部依赖，和 Python 版本绑定，不存在兼容问题。缺点是功能有限——只管隔离，不管依赖解析和锁定。

virtualenv ##

virtualenv 是 venv 的前身，功能更强但需要单独安装：

pip install virtualenv
virtualenv .venv
source .venv/bin/activate

比 venv 多的能力包括：更快（通过缓存和 AppData 种子）、支持 bootstrap 脚本、可指定任意 Python 解释器创建环境。

ps: 新项目直接用 venv 就好。virtualenv 的优势主要在旧版本 Python（3.3 以前）或需要自定义创建流程的场景，日常开发不需要专门装它。

conda 环境 ##

conda 走的是另一条路——它不只是 Python 的虚拟环境，而是通用的包和环境管理器。能装 Python 包，也能装 C/C++ 库、R 包，甚至 CUDA toolkit。

conda create -n myenv python=3.10
conda activate myenv

这才是 conda 真正的价值：你不需要额外折腾系统级依赖。数据科学、机器学习项目里经常碰到 numpy 装不上的情况——缺 BLAS/LAPACK 库、缺 Fortran 编译器，conda 直接帮你把这些非 Python 依赖也管了。

ps: 如果不涉及数据科学，conda 太重了。安装包几百 MB，解析依赖还慢。普通 Python 后端项目用 venv + pip 就够。

Python 版本管理 ##

一个机器上可能要同时跑 Python 3.8、3.10、3.12。原因很现实——有的老项目就是跑不了高版本，有的库还没适配新 Python，但新项目又想用新语法。

pyenv ##

pyenv 是目前最成熟的 Python 版本管理方案。能装、能切、能按目录锁定版本：

# 安装
brew install pyenv           # macOS
# Linux 参考: https://github.com/pyenv/pyenv#installation

# 使用
pyenv install 3.10.4
pyenv global 3.10.4          # 全局默认
pyenv local 3.9.7            # 当前目录锁定 3.9.7

pyenv local 会在当前目录生成一个 .python-version 文件，cd 进去自动切换版本，非常顺手。

pyenv 的原理是通过 PATH 劫持——在 PATH 前面插入 shim 脚本，根据 .python-version 决定实际调用哪个版本的 Python 解释器。

conda 的版本管理 ##

conda 创建环境时可以直接指定 Python 版本，本质上是把 Python 当作一个 conda 包来管理：

conda create -n py39 python=3.9
conda create -n py310 python=3.10

ps: 如果只做 Python 开发，pyenv 比 conda 轻得多。conda 的版本管理是和它的环境管理绑定的，你不装 conda 环境就切不了版本。

依赖锁定：从 requirements.txt 到 Poetry ##

虚拟环境解决了隔离问题，但没解决"我和同事装的依赖是不是完全一样"的问题。

requirements.txt 的局限 ##

最常见的做法是 pip freeze > requirements.txt。问题在于 pip freeze 会把所有间接依赖也导出来，而且锁的是精确版本：

numpy==1.24.3
pandas==2.0.1
python-dateutil==2.8.2
six==1.16.0
...

这带来两个麻烦：

  1. 跨平台问题：requirements.txt 里可能混入了平台相关的包（如 Windows 上的 pywin32），换个系统就装不上。
  2. 依赖升级困难：所有包都锁死，要升级一个直接依赖，得手动解整个依赖链。

更好的做法是区分"直接依赖"和"锁定文件"：一个文件列出你主动安装的包（宽松版本约束），另一个文件锁定所有依赖的精确版本（可复现）。

pip-tools：最小侵入的改进 ##

如果你不想换工作流，只是想改善 requirements.txt 的维护体验，pip-tools 是最轻量的选择：

pip install pip-tools

在 requirements.in 中写直接依赖：

django>=4.0
requests

然后：

pip-compile requirements.in    # 生成 requirements.txt（完整的锁定依赖）
pip-sync requirements.txt      # 将环境同步为 requirements.txt 中记录的精确版本

ps: pip-sync 会卸载不在 requirements.txt 中的包，这一点很关键——它保证了环境真的和锁定文件一致，而不是"装上了就行，多余的不管"。

Pipenv：曾经官方推荐的方案 ##

Pipenv 引入了 Pipfile 和 Pipfile.lock 的概念，和 Node.js 的 package.json / package-lock.json 类似：

pip install pipenv
pipenv install requests       # 安装并更新 Pipfile / Pipfile.lock
pipenv shell                  # 激活环境

想法很好，但 Pipenv 的依赖解析一直是个槽点——慢，出了名的慢。一个中等规模的项目，pipenv lock 跑几分钟是常有的事。社区里抱怨不少，维护节奏也不稳定。

除非团队已经在用 Pipenv 且没遇到性能问题，否则新项目不建议选它。

Poetry：当前最成熟的方案 ##

Poetry 把依赖管理、虚拟环境、打包发布整合到一起了：

pip install poetry
poetry new myproject          # 创建新项目（可选）
poetry add requests           # 安装并更新 pyproject.toml
poetry install                # 按 poetry.lock 安装
poetry shell                  # 激活虚拟环境

几个我喜欢的地方：

  • 依赖解析快：比 Pipenv 快得多，用的是 SAT solver。
  • pyproject.toml 是标准：PEP 517/518/621 已经把 pyproject.toml 定为 Python 项目的元数据标准文件，Poetry 原生支持。
  • 一条命令打包发布：poetry build && poetry publish。

Poetry 的问题在于它对项目结构有一定的"主张"——poetry new 创建的项目有固定的目录布局。不过这不是硬性要求，对现有项目 poetry init 也能用。

怎么选 ##

场景推荐
个人小脚本、一次性项目venv + pip + requirements.txt
团队项目、需要可复现构建venv + Poetry（或 pip-tools）
数据科学、需要非 Python 依赖conda + environment.yml
有 CI/CD 要求、不想改现有流程pip-tools

ps: 如果你在选型，Poetry 是当前最平衡的选择。它不像 conda 那么重，又比 pip-tools 多了打包和发布的能力。但 pip-tools 对现有流程的侵入最小——只加一个 requirements.in 文件，其他照旧。

CI/CD 中的实践 ##

锁定文件（poetry.lock、Pipfile.lock、requirements.txt）必须纳入版本控制。CI 环境按锁定文件安装，保证和开发环境一致。

一个典型的 GitHub Actions 配置（以 Poetry 为例）：

name: CI

on: [push, pull_request]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        python-version: ["3.9", "3.10", "3.11"]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: ${{ matrix.python-version }}
      - name: Install dependencies
        run: |
          pip install poetry
          poetry install
      - name: Run tests
        run: poetry run pytest

多版本测试矩阵是值得花的成本。Python 版本间的 breaking change 不算频繁，但一旦踩到就很隐蔽——比如 3.9 → 3.10 的类型注解语法变化，| 联合类型的语法在 3.10 才支持，CI 不测就没人发现。

另外注意 CI 的依赖缓存。Poetry 的缓存目录是 ~/.cache/pypoetry，pip 的是 ~/.cache/pip，配好 actions/cache 能省不少构建时间。

发布到 PyPI ##

如果要发布自己的包，Poetry 的流程最省事：

poetry build
poetry publish --repository testpypi   # 先测试发布
poetry publish                         # 正式发布

几个要点：

  • 先发 Test PyPI验证。Test PyPI 和正式 PyPI 是独立的两套服务，先在 Test 上确认包能正常安装再推到正式站。
  • 版本号遵循语义化版本（SemVer）。MAJOR.MINOR.PATCH，不向下兼容的改 MAJOR，加新功能改 MINOR，修 bug 改 PATCH。
  • pyproject.toml 中填好元数据：name、version、description、authors、license、readme。PyPI 页面上的展示全靠这些。

ps: flit 是另一个轻量的打包工具，如果只是打包发布、不需要依赖管理的功能，flit 比 Poetry 更简单。但大多数项目已经在用 Poetry 管依赖了，再加一个 flit 没必要——Poetry 的打包能力虽然不如 flit 专注，但够用。

总结 ##

选择工具的核心原则是：用最少的工具覆盖你需要的能力，同时保持团队一致性。

对于大多数 Python 开发场景，我的推荐组合是：

通用 Web/后端项目

  • pyenv 管 Python 版本
  • venv 创建虚拟环境（Poetry 默认也用它）
  • poetry 管依赖 + 锁定 + 打包

数据科学 / 机器学习

  • conda 管一切——Python 版本、环境、非 Python 依赖
  • environment.yml 锁定环境

老项目，不想折腾

  • pip-tools——最小侵入，只改善 requirements.txt 的管理，不改别的。

无论选哪套，锁定文件（poetry.lock / requirements.txt / environment.yml）一律进版本控制。看起来是句废话，但我真见过不少项目没把 lock 文件纳入 Git——每次部署依赖版本都可能不一样，出了问题根本没法复现。
