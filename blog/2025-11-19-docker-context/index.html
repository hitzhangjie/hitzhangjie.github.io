Docker Context：一套 CLI，切换多个容器运行时

Posted 2025-11-19 00:00 +0800 by ZhangJie ‐ 3 min read

分享:  

背景 #

如果你在 macOS 上用过 Docker，大概率不止用过一种方案。最早可能是 Docker Desktop，后来因为资源占用换了 Colima，又听说过 Podman 和 Lima，甚至在不同项目间来回切换。每换一次就要改 DOCKER_HOST 环境变量、改 socket 路径，一不留神就连不上 daemon，然后对着 Cannot connect to the Docker daemon 发呆。

其实 Docker 官方早就提供了一个机制来管理这种多后端切换——Docker Context。一个 context 本质上就是一组 Docker daemon 的连接配置，docker context 子命令让你可以在不同 daemon 之间一键切换，不用再手动折腾环境变量。

Docker Context 是什么 #

简单说，一个 Docker Context 保存了：

  • Docker daemon 的连接地址（socket 路径或 TCP 地址）
  • TLS 配置（是否需要验证、CA 证书等）
  • 可选的描述信息

用 docker context ls 可以看到当前所有可用的 context：

$ docker context ls
NAME              TYPE      DESCRIPTION                    DOCKER ENDPOINT
colima *          moby      colima                         unix:///Users/zhangjie/.colima/default/docker.sock
default           moby      Current DOCKER_HOST based...   unix:///var/run/docker.sock
desktop-linux     moby      Docker Desktop                 unix:///Users/zhangjie/.docker/run/docker.sock

带 * 的是当前激活的 context。切换只需要一行：

docker context use colima

之后所有的 docker 命令都会自动发到 Colima 的 daemon，不需要设任何环境变量。

几种常见的容器方案作为 Context #

macOS 上没有原生的 Linux 容器支持，各种方案本质上都是在 Linux VM 里跑一个 Docker daemon，然后通过 socket 暴露给宿主机的 docker CLI。它们之间的区别主要在于 socket 路径不同：

方案Socket 路径
Docker Desktopunix:///Users/<user>/.docker/run/docker.sock
Colimaunix:///Users/<user>/.colima/default/docker.sock
Rancher Desktopunix:///Users/<user>/.rd/docker.sock
Podman（通过 podman machine）unix:///Users/<user>/.local/share/containers/podman/machine/podman-machine-default/podman.sock
Lima（手动配置 dockerd）取决于 VM 配置，通常是 unix:///Users/<user>/.lima/<instance>/sock/docker.sock

安装这些工具时，它们通常会通过 docker context create 自动注册对应的 context，所以装完后 docker context ls 就能看到。

如果要手动创建 context，也很直观：

# 创建一个指向特定 socket 的 context
docker context create my-custom --docker "host=unix:///path/to/docker.sock"

底层是怎么实现的 #

docker context ls 执行时，实际做了这么几件事：

1. 扫描配置目录 ##

Docker CLI 读取 ~/.docker/contexts/meta/ 下的所有子目录。每个子目录以 context 的哈希值命名，里面只有一个 meta.json：

$ tree ~/.docker/
├── config.json              # 存储 currentContext
└── contexts/
    └── meta/
        ├── a1b2c3d4.../
        │   └── meta.json    # colima context 配置
        └── e5f6g7h8.../
            └── meta.json    # desktop-linux context 配置

看看 meta.json 里面有什么：

$ for i in `find ~/.docker/contexts/ -name meta.json`; do cat $i | jq ; done
{
  "Name": "colima",
  "Metadata": {
    "Description": "colima"
  },
  "Endpoints": {
    "docker": {
      "Host": "unix:///Users/zhangjie/.colima/default/docker.sock",
      "SkipTLSVerify": false
    }
  }
}
{
  "Name": "desktop-linux",
  "Metadata": {
    "Description": "Docker Desktop"
  },
  "Endpoints": {
    "docker": {
      "Host": "unix:///Users/zhangjie/.docker/run/docker.sock",
      "SkipTLSVerify": false
    }
  }
}

每个 meta.json 包含：

  • Name：context 的显示名称
  • Metadata.Description：描述信息
  • Endpoints.docker.Host：Docker daemon 的连接地址

2. 添加内置 context ##

除了从 meta/ 目录读出来的，Docker CLI 还会自动补两个内置 context：

  • default：硬编码指向 unix:///var/run/docker.sock（Linux 上的默认 socket）
  • 基于当前 DOCKER_HOST 环境变量动态生成

这就是为什么即使 ~/.docker/contexts/meta/ 是空的，docker context ls 也至少会显示 default。

3. 确定当前激活的 context ##

~/.docker/config.json 中的 currentContext 字段记录了当前用的是哪个 context：

{
  "auths": { ... },
  "currentContext": "colima",
  "plugins": { ... }
}

docker context ls 读取这个字段，在对应 context 后面显示 *。docker context use <name> 本质上就是修改这个字段的值。

我遇到过的坑 #

在 Colima、Docker Desktop、Podman 之间反复切换时，有几个容易踩的坑：

Context 名称冲突。有些工具安装时会尝试创建同名的 context，如果之前已经存在就会失败或覆盖。比如先装了 Colima，又装了 Docker Desktop，两个都想注册自己的 context，有时候行为不太一致。遇到这种情况可以先 docker context rm 清理掉旧的，再重新创建。

当前 context 指向的 daemon 没启动。这是最常见的报错来源——docker context ls 只检查配置文件是否存在，不会验证 daemon 是否真的在运行。所以可能你切到了 colima，但 Colima VM 没启动，然后 docker ps 就报 Cannot connect to the Docker daemon。解决方案很简单：先用对应工具启动 VM（colima start / podman machine start），再执行 docker 命令。

Socket 权限问题。不同方案的 socket 文件权限设置不同。Docker Desktop 通常会把 socket 放在用户有权限的路径，但有些方案（尤其是 Lima 手动配置的）可能需要把用户加入特定组或者 sudo chmod 调整 socket 权限。

DOCKER_HOST 环境变量会覆盖 context。这是最容易忽略的一点。Docker CLI 的优先级是：DOCKER_HOST 环境变量 > 当前 context。如果你之前为了临时切换设置了 DOCKER_HOST，后来忘了 unset，那么 docker context use 切了也没用，实际连接的还是 DOCKER_HOST 指向的 daemon。排查时可以先用 docker info 看实际连接的 daemon 信息，或者直接 unset DOCKER_HOST。

总结 #

Docker Context 提供了一个干净的抽象层，让你用同一套 docker CLI 命令在不同容器后端之间切换。理解它的底层存储结构后，排查配置问题会容易很多：

  • ~/.docker/contexts/meta/<hash>/meta.json — context 配置
  • ~/.docker/config.json 中的 currentContext — 当前激活的 context
  • DOCKER_HOST 环境变量会覆盖 context，是常见的坑
  • Context 只检查配置文件，不验证 daemon 是否运行

日常使用记住这几个命令就够了：

docker context ls          # 查看所有 context
docker context use <name>  # 切换
docker context create ...  # 手动创建
docker context rm <name>   # 删除
