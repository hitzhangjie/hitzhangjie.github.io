SigNoz Docker Compose 配置解读：从架构到编排的映射

Posted 2026-07-29 12:00 +0800 by ZhangJie ‐ 4 min read

分享:  

背景 #

在上一篇中我们拆解了 SigNoz 的整体架构：OTel Collector 采数据、ClickHouse 存数据、SigNoz Server 查数据、Schema Migrator 管表结构、Zookeeper 做集群协调。

这篇我们来看这套架构是如何被翻译成一组 Docker Compose 服务的。理解了架构之后，每个 service 的配置项就不是孤立的参数，而是对架构中某个设计决策的具体实现。反过来，读配置也能帮你验证架构理解是否正确。

本文分析的配置文件来自 signoz/deploy/docker/docker-compose.yaml（v0.107.0 附近版本）。

配置总览 #

整个 compose 文件分为四个逻辑块：

  • 几个 YAML 锚点（x-*）——复用的配置片段
  • 8 个 services——架构中各组件的容器化实例
  • 1 个 network——signoz-net 桥接网络
  • 3 个 named volumes——持久化数据卷

在逐个服务展开之前，先理解 YAML 锚点这个设计——它为整个配置文件奠定了可维护性的基础。

YAML 锚点：DRY 配置 #

你会在文件中看到很多以 x- 开头的块——这不是 Docker Compose 的保留字，而是 YAML 语法层面的东西。Docker Compose 会忽略以 x- 开头的顶级元素，这让它们成为定义可复用配置片段的理想选择。

文件中定义了四个锚点，形成了清晰的复用层级：

x-common (基础配置)
  └── networks, restart, logging

x-clickhouse-defaults (ClickHouse 相关)
  └── !!merge <<: *common     ← 继承 x-common
      + image, labels, depends_on, healthcheck, ulimits, environment

x-zookeeper-defaults (Zookeeper 相关)
  └── !!merge <<: *common     ← 继承 x-common
      + image, labels, healthcheck

x-db-depend (依赖数据库的服务)
  └── !!merge <<: *common     ← 继承 x-common
      + depends_on: clickhouse, schema-migrator-sync

!!merge <<: *common 是 YAML 的合并语法——*common 引用锚点，<<: 将其内容合并到当前位置。假设 x-common 定义了 networks、restart、logging，那么 clickhouse 服务最终的配置就是这三项加上自己在 x-clickhouse-defaults 和 service 定义中追加的内容。

这种层级设计不是炫技——它对应了 SigNoz 架构中的依赖关系。所有服务共享网络和重启策略（x-common），依赖数据库的服务（signoz、otel-collector、schema-migrator-async）需要等 ClickHouse 就绪（x-db-depend）。锚点让这些关系在配置中一目了然。

服务逐项解读 #

init-clickhouse：自定义函数初始化 ##

init-clickhouse:
  !!merge <<: *common
  image: clickhouse/clickhouse-server:25.5.6
  container_name: signoz-init-clickhouse
  command:
    - bash
    - -c
    - |
      # 下载 histogramQuantile 自定义函数的二进制文件
      wget -O histogram-quantile.tar.gz "https://github.com/SigNoz/signoz/releases/..."
      tar -xvzf histogram-quantile.tar.gz
      mv histogram-quantile /var/lib/clickhouse/user_scripts/histogramQuantile
  restart: on-failure
  volumes:
    - ../common/clickhouse/user_scripts:/var/lib/clickhouse/user_scripts/

这个服务是"一次性任务"——它的唯一使命是在 ClickHouse 启动前下载 histogramQuantile 自定义函数。为什么需要这个？

ClickHouse 内置的聚合函数（如 avg、quantile）不足以满足可观测性场景中的分位数计算需求——比如计算 P95、P99 延迟时，你不想存储每个原始数据点，而是希望用直方图近似计算。histogramQuantile 就是 SigNoz 实现的这样一个自定义函数，它读取 ClickHouse 中的直方图数据并估算分位数。

几个细节：

  • restart: on-failure 而不是 unless-stopped——任务完成后不需要常驻，但失败了要重试（网络问题、GitHub 不可用等）
  • 挂载 user_scripts 目录到宿主机——因为 ClickHouse 容器也需要访问同一个文件，共享 Volume 是最简单的方案
  • 复用了 x-common 锚点只保留了网络和日志配置，没有引入不必要的 depends_on

zookeeper-1：为 ClickHouse 集群预留 ##

zookeeper-1:
  !!merge <<: *zookeeper-defaults
  container_name: signoz-zookeeper-1
  volumes:
    - zookeeper-1:/bitnami/zookeeper
  environment:
    - ZOO_SERVER_ID=1
    - ALLOW_ANONYMOUS_LOGIN=yes
    - ZOO_AUTOPURGE_INTERVAL=1
    - ZOO_ENABLE_PROMETHEUS_METRICS=yes

前面架构篇说过：单机 ClickHouse 不需要 Zookeeper，但 ClickHouse 集群（多副本 ReplicatedMergeTree）需要它来做副本协调。SigNoz 默认部署了 Zookeeper-1，命名留了数字后缀（zookeeper-1），意味着生产环境可以扩展为 Zookeeper 集群（zookeeper-2、zookeeper-3 形成 Quorum）。

健康检查用的是 Zookeeper 的四字命令 ruok（“are you ok”）：curl http://localhost:8080/commands/ruok | grep error | grep null——返回 imok 表示正常，返回包含 error 且 null 表示异常。

ZOO_AUTOPURGE_INTERVAL=1 设置自动清理间隔为 1 小时（默认不清理），避免 Zookeeper 快照和日志把磁盘占满——这个小配置在实际运维中经常被忽略。

clickhouse：核心存储引擎 ##

clickhouse:
  !!merge <<: *clickhouse-defaults
  container_name: signoz-clickhouse
  volumes:
    - ../common/clickhouse/config.xml:/etc/clickhouse-server/config.xml
    - ../common/clickhouse/users.xml:/etc/clickhouse-server/users.xml
    - ../common/clickhouse/custom-function.xml:/etc/clickhouse-server/custom-function.xml
    - ../common/clickhouse/user_scripts:/var/lib/clickhouse/user_scripts/
    - ../common/clickhouse/cluster.xml:/etc/clickhouse-server/config.d/cluster.xml
    - clickhouse:/var/lib/clickhouse/

这是整个 SigNoz 的核心——所有遥测数据都存在这里。来看几个关键配置。

启动依赖：它要求 init-clickhouse 完成且 zookeeper-1 健康。init-clickhouse 先把自定义函数下载好，Zookeeper 先就绪——ClickHouse 启动时会连接 Zookeeper 注册自己的副本信息，如果 Zookeeper 还没起来，ClickHouse 也能启动但复制功能不可用。

五个配置文件 + 一个数据卷：

文件作用
config.xmlClickHouse 主配置：端口、日志、监听地址等
users.xml用户和权限配置
custom-function.xml注册 histogramQuantile UDF，指向 /var/lib/clickhouse/user_scripts/histogramQuantile
cluster.xml集群拓扑定义（分片、副本），单机模式下通常定义一个本地 shard
user_scripts/自定义函数二进制文件目录（即 init-clickhouse 下载后存放的位置）
clickhouse:/var/lib/clickhouse/named volume，持久化所有表数据——这是最重要的 volume，删了就数据全无

健康检查：wget --spider -q 0.0.0.0:8123/ping。8123 是 ClickHouse 的 HTTP 端口，/ping 端点返回 “Ok."。这个检查比 TCP 端口探测可靠，因为它能验证 ClickHouse 的 HTTP 服务确实在响应。

资源限制：ulimits 将 nproc 设为 65535、nofile 设为 262144。ClickHouse 在高并发场景下会打开大量文件（数据文件 + 索引文件）和进程（后台 Merge/Mutation 操作），默认的 1024 上限完全不够用。

schema-migrator-sync 和 schema-migrator-async ##

schema-migrator-sync:
  command:
    - sync
    - --dsn=tcp://clickhouse:9000
    - --up=
  restart: on-failure

schema-migrator-async:
  !!merge <<: *db-depend
  command:
    - async
    - --dsn=tcp://clickhouse:9000
    - --up=
  restart: on-failure

两个 migrator 都连同一个 ClickHouse DSN（tcp://clickhouse:9000，9000 是 ClickHouse 的 Native Protocol 端口），但行为和依赖不同：

  • sync migrator：只依赖 clickhouse 健康，不需要 db-depend。它是最早执行的那一批——ClickHouse 一就绪就开始跑，跑完其他依赖数据库的服务才能启动。--up= 表示迁移到最新版本。
  • async migrator：依赖 x-db-depend（即 clickhouse + sync migrator 都完成），在后台执行非关键迁移。

为什么需要两个？因为 ClickHouse 的某些 DDL 操作（如创建带 MATERIALIZED 的视图）可能比较慢。如果是关键的表结构变更（比如新加了必填字段），你必须等它执行完才能让 Collector 往里写数据。如果是非关键的变更（比如一个不紧急的聚合视图），后台慢慢跑就行，不用阻塞服务启动。

连接选择 Native Protocol（9000）而不是 HTTP（8123）——因为 DDL 操作通过 Native Protocol 更高效，且支持 ClickHouse 自定义的扩展语法。

signoz：后端服务与 UI ##

signoz:
  !!merge <<: *db-depend
  image: signoz/signoz:${VERSION:-v0.107.0}
  command:
    - --config=/root/config/prometheus.yml
  ports:
    - "8080:8080"
  volumes:
    - ../common/signoz/prometheus.yml:/root/config/prometheus.yml
    - ../common/dashboards:/root/config/dashboards
    - sqlite:/var/lib/signoz/
  environment:
    - SIGNOZ_ALERTMANAGER_PROVIDER=signoz
    - SIGNOZ_TELEMETRYSTORE_CLICKHOUSE_DSN=tcp://clickhouse:9000
    - SIGNOZ_SQLSTORE_SQLITE_PATH=/var/lib/signoz/signoz.db
    - DASHBOARDS_PATH=/root/config/dashboards
    - STORAGE=clickhouse
    - GODEBUG=netdns=go
    - TELEMETRY_ENABLED=true
    - DEPLOYMENT_TYPE=docker-standalone-amd
    - DOT_METRICS_ENABLED=true

这是 SigNoz 的"大脑”，把所有能力打包在一个镜像里。对照架构篇来理解每个环境变量：

环境变量对应架构概念
STORAGE=clickhouse存储引擎选型——ClickHouse 存遥测数据
SIGNOZ_TELEMETRYSTORE_CLICKHOUSE_DSN=tcp://clickhouse:9000SigNoz Server 连接 ClickHouse 的地址，服务名就是 hostname（Compose 网络内的 DNS）
SIGNOZ_SQLSTORE_SQLITE_PATH=/var/lib/signoz/signoz.db元数据（告警规则、用户、渠道配置）存在 SQLite
SIGNOZ_ALERTMANAGER_PROVIDER=signoz告警引擎使用 SigNoz 内置实现（而非外部 AlertManager）
DASHBOARDS_PATH=/root/config/dashboardsDashboard 的 JSON 定义文件路径
DEPLOYMENT_TYPE=docker-standalone-amd部署模式标识，SigNoz 借此调整某些参数（如资源限制建议）
GODEBUG=netdns=go强制使用 Go 原生 DNS 解析（而非 cgo），避免某些容器 DNS 问题

prometheus.yml 作为命令行参数传入。这个文件是 SigNoz 告警规则引擎的内部配置，借用 Prometheus 的规则定义格式——不是用来连接外部 Prometheus 的。

端口映射 8080:8080 暴露了 SigNoz Web UI。访问 http://localhost:8080 就是完整的可观测性界面。

otel-collector：数据入口 ##

otel-collector:
  !!merge <<: *db-depend
  image: signoz/signoz-otel-collector:${OTELCOL_TAG:-v0.129.12}
  command:
    - --config=/etc/otel-collector-config.yaml
    - --manager-config=/etc/manager-config.yaml
    - --copy-path=/var/tmp/collector-config.yaml
    - --feature-gates=-pkg.translator.prometheus.NormalizeName
  ports:
    - "4317:4317"     # OTLP gRPC
    - "4318:4318"     # OTLP HTTP
  volumes:
    - ./otel-collector-config.yaml:/etc/otel-collector-config.yaml
    - ../common/signoz/otel-collector-opamp-config.yaml:/etc/manager-config.yaml
  environment:
    - OTEL_RESOURCE_ATTRIBUTES=host.name=signoz-host,os.type=linux
    - LOW_CARDINAL_EXCEPTION_GROUPING=false
  depends_on:
    signoz:
      condition: service_healthy

架构篇说过，Collector 是数据入口。这里的配置有几个值得注意的点：

--config 和 --manager-config 的双配置机制：otel-collector-config.yaml 定义常规的 Pipeline（receivers → processors → exporters），manager-config.yaml 是 OpAMP（Open Agent Management Protocol）的配置。OpAMP 允许远程管理 Collector——SigNoz Cloud 场景下，你可以通过一个中央控制面下发新的 Pipeline 配置，批量更新所有 Collector。

--copy-path：Collector 启动后把当前生效的配置拷贝到指定路径，方便调试和状态检查。

--feature-gates=-pkg.translator.prometheus.NormalizeName：关闭指标名标准化。默认情况下，OTel 会把 Prometheus 指标名中的非字母数字字符替换为下划线（如 http.requests.total → http_requests_total）。SigNoz 选择保留原始命名，因为用户通过 SigNoz UI 配置告警时引用的是原始指标名，标准化后的名字会与用户预期不一致。

对 signoz 的依赖：Collector 依赖 SigNoz Server 的健康状态。这个依赖不是技术上的必然（Collector 可以直接往 ClickHouse 写数据），而是部署时序上的考虑——确保 SigNoz 的 Web UI 在数据开始流入之前就可用，避免用户看到"空数据"而困惑。

schema-migrator-async 虽然也用了 x-db-depend（依赖 clickhouse + schema-migrator-sync），但它不依赖 signoz，因为表结构迁移不需要 Web UI。

服务依赖链总结：

zookeeper-1 ──┐
              ├──► clickhouse ────► schema-migrator-sync ──┐
init-clickhouse┘                                             │
                                                    ┌────────┘
                                                    ├──► signoz ──► otel-collector
                                                    └──► schema-migrator-async

网络与数据卷 #

signoz-net ##

networks:
  signoz-net:
    name: signoz-net

一个自定义 bridge 网络。所有服务都在这个网络内，用服务名（clickhouse、signoz、zookeeper-1）作为 DNS 主机名互相通信。这是 Docker Compose 的默认行为，但显式创建网络可以避免与其他 compose 项目共享默认网络。

配置中出现的连接串全部使用服务名：tcp://clickhouse:9000、tcp://clickhouse:9000——这就是 Compose 网络的内置 DNS 在工作。

数据卷 ##

volumes:
  clickhouse:
    name: signoz-clickhouse
  sqlite:
    name: signoz-sqlite
  zookeeper-1:
    name: signoz-zookeeper-1

三个 named volumes 对应三种持久化需求：

Volume内容丢失后果
clickhouse所有遥测数据（Traces、Metrics、Logs）历史数据全部丢失，不可恢复
sqlite告警规则、通知渠道、用户、Dashboard配置全丢，需要重新手动配置
zookeeper-1Zookeeper 快照和事务日志如果只是单机 ClickHouse，影响不大；如果是集群，会导致副本元数据丢失

这些 volumes 在 docker-compose down 时不会被自动删除——这是默认行为，防止误操作导致数据丢失。如果要彻底清理，需要加 -v 参数：docker-compose down -v。

总结 #

从架构到配置的映射关系，一句话概括：

架构组件Compose Service核心职责
OTel Collectorotel-collector接收 OTLP 数据，写入 ClickHouse
核心存储clickhouse列式存储所有遥测数据
元数据存储SQLite（在 signoz 容器内）存储告警规则、用户等
查询 + 告警 + UIsignozWeb UI、告警引擎、查询服务
表结构管理schema-migrator-sync/asyncClickHouse DDL 变更
集群协调zookeeper-1ClickHouse 集群副本协调
初始化init-clickhouse下载自定义函数

理解了这个映射关系，再去看 docker-compose.yaml，每一行配置都能回溯到架构设计中的某个决策——环境变量是组件间的"接口契约"，volume 是持久化策略的落地，健康检查是启动顺序的保证。

这也是一个很好的案例：一个设计良好的系统，其部署配置本身就是架构文档的另一种表达。当架构清晰时，配置自然就"自解释"了。
