Go 调度器 M 的诞生与消亡：从一次 go 语句到线程创建/复用的完整路径 #

源码版本：go1.22.2（release-branch.go1.22）。所有行号均对应该版本的 src/runtime/proc.go 等文件。 阅读本文前建议先了解 G/M/P 三件套的基本概念：G 是 goroutine，M 是 OS 线程（机器），P 是执行 Go 代码所必需的"处理器"资源（proc.go:24-29）。

很多人问过这样一个问题：一个 Go HTTP 服务，从 0 请求到请求量变大，那些执行 goroutine 的线程（M）到底是怎么冒出来的？

直觉上可能是"每创建一个 goroutine 就创建一条线程"——错；也可能是"启动时就把线程都建好"——也错。真相是：

P 启动时全量预创建（GOMAXPROCS 个），M 一个都不预创建（只有进程自带的 m0），全部按需惰性创建，且创建后几乎永不销毁。

下面从 go 语句这条主线出发，把 M 的创建路径、创建决策依据、复用机制、退出条件对着源码过一遍，最后用 HTTP 服务把整个生命周期串起来。

一、启动时：P 全量预创建，M 只此一家 ##

程序一启动，schedinit()（proc.go:750）里执行：

procs := ncpu
if n, ok := atoi32(gogetenv("GOMAXPROCS")); ok && n > 0 {
    procs = n
}
if procresize(procs) != nil {   // proc.go:827
    throw("unknown runnable goroutine during bootstrap")
}

procresize 一次性分配 GOMAXPROCS 个 P，状态全部是 _Pidle，挂在 sched.pidle 空闲链表上。注意：此时一个 M 都没有。进程只有一个 OS 线程——m0（proc.go:116 的全局变量），它跑着 g0 和 main goroutine。

随后 runtime.main（proc.go:168-173）做了两件事：

// Allow newproc to start new Ms.
mainStarted = true
if GOARCH != "wasm" { // no threads on wasm yet, so no sysmon
    systemstack(func() {
        newm(sysmon, nil, -1)   // 创建 sysmon 监控线程
    })
}

sysmon 是唯一的"预置"线程：它不占 P，负责抢占、把卡在 syscall 里的 P 抢回来、netpoll 超时等。除此之外，所有 M 都是按需创建的。

所以 0 请求时：8 核机器 = 8 个 idle P + 1 个 m0 + 1 个 sysmon。

二、go 语句的完整路径：newproc → 入队 → wakep ##

go f() 会被编译器翻译成对 runtime.newproc(f) 的调用（Go 1.17 起是寄存器 ABI，直接把函数值指针传进去）。它的完整实现（proc.go:4874）：

// Create a new g running fn.
// Put it on the queue of g's waiting to run.
// The compiler turns a go statement into a call to this.
func newproc(fn *funcval) {
    gp := getg()
    pc := getcallerpc()
    systemstack(func() {            // 切到系统栈（g0）执行
        newg := newproc1(fn, gp, pc)    // ① 造出 G（状态 _Grunnable）

        pp := getg().m.p.ptr()
        runqput(pp, newg, true)         // ② 入队（next=true → runnext）

        if mainStarted {
            wakep()                     // ③ 尝试多拉一个 M 来跑
        }
    })
}

2.1 newproc1：造 G（proc.go:4892） ##

newg := gfget(pp)            // ① 先从 P 的 gFree 空闲池捞，池子空才新建
if newg == nil {
    newg = malg(stackMin)    // 分配 2KB 栈（stackMin）
    casgstatus(newg, _Gidle, _Gdead)
    allgadd(newg)            // 挂进 allg 全局 G 表（GC 可见）
}
...
newg.sched.pc = abi.FuncPCABI0(goexit) + sys.PCQuantum  // 返回地址是 goexit
gostartcallfn(&newg.sched, fn)         // 压入要执行的函数
...
casgstatus(newg, _Gdead, _Grunnable)   // ★ 状态置为可运行
...
newg.goid = pp.goidcache               // goid 每 P 批量缓存，避免全局原子

两个细节：

  • G 也是池化复用的：gfget（proc.go:5072）优先从 P 的 gFree 池取，取不到才 malg 新分配。这也是并发量回落后再涨时开销极低的原因。
  • goid 按 GoidCacheBatch 批量从全局计数器领到每个 P 上，避免每次创建都打全局原子。

2.2 runqput：入队决策（proc.go:6635） ##

func runqput(pp *p, gp *g, next bool) {
    if next {                       // ★ newproc 传 true
    retryNext:
        oldnext := pp.runnext
        if !pp.runnext.cas(oldnext, guintptr(unsafe.Pointer(gp))) {
            goto retryNext          // 自旋 CAS：别的 P 可能并发偷 runnext
        }
        if oldnext == 0 {
            return                  // runnext 本来空 → 完事
        }
        gp = oldnext.ptr()          // 原 runnext 被挤到普通队列
    }

retry:
    h := atomic.LoadAcq(&pp.runqhead)
    t := pp.runqtail
    if t-h < uint32(len(pp.runq)) {        // local 256 格没满
        pp.runq[t%uint32(len(pp.runq))].set(gp)
        atomic.StoreRel(&pp.runqtail, t+1) // 无锁入队
        return
    }
    if runqputslow(pp, gp, h, t) {         // 满了 → 挪一半 + 新 G 到 global
        return
    }
    goto retry
}

入队优先级：新 G 先进当前 P 的 runnext（下一条立即被调度），其次 local 环形队列（runtime2.go:668 的 runq [256]guintptr），满了才由 runqputslow（proc.go:6670）把 local 里一半 + 新 G 一起溢出到 global 队列（sched.runq，受 sched.lock 保护）。

2.3 wakep：要不要多拉一个 M（proc.go:2975） ##

这是 M 创建决策的第一道闸门：

func wakep() {
    // Be conservative about spinning threads, only start one if none exist
    // already.
    if sched.nmspinning.Load() != 0 || !sched.nmspinning.CompareAndSwap(0, 1) {
        return                        // 已有 spinning M / CAS 竞争失败 → 不创建
    }

    mp := acquirem()
    var pp *p
    lock(&sched.lock)
    pp, _ = pidlegetSpinning(0)       // 必须能拿到一个 idle P
    if pp == nil {
        ... 回滚 nmspinning ...
        return                        // 没有 idle P → 不创建
    }
    unlock(&sched.lock)

    startm(pp, true, false)           // spinning=true：新 M 起来后先去"偷活"
    releasem(mp)
}

wakep 的创建条件（两条同时满足）：

  1. 当前没有 spinning M（sched.nmspinning == 0，且 CAS 成功抢到"增员名额"）；
  2. 存在 idle P 可以分给新 M。

如果系统里已经有一个 M 正在 spinning（自旋找活干），说明"马上会有人来拿这份工作"，就不再拉新线程——这是防止线程抖动（thrashing）的关键。

...

M 创建的真正决策点就在这里：mget() 空闲池为空才 newm。 有新工作 + 有 idle P + 没有空闲 M 可复用 → 建线程。这是全程唯一"依据"。

2.5 newm → newm1 → newosproc：真正建线程 ##

func newm(fn func(), pp *p, id int64) {
    acquirem()                       // 关抢占，保证 allm 里新 M 必然会被启动
    mp := allocm(pp, fn, id)         // new(m) + mcommoninit（挂 allm）+ 分配 g0 栈
    mp.nextp.set(pp)                 // ★ 把要接管的 P 存在 nextp
    mp.sigmask = initSigmask
    if gp := getg(); ...(lockedExt != 0 || gp.m.incgo) ... {
        ...交给 templateThread...    // 在锁定线程/cgo 线程上不能自己 clone
    }
    newm1(mp)
    releasem(getg().m)
}

// proc.go:2680
func newm1(mp *m) {
    if iscgo {
        ... _cgo_thread_start ...    // cgo 程序用 pthread_create
        return
    }
    execLock.rlock() // Prevent process clone.
    newosproc(mp)                    // 非 cgo → 直接 clone 系统调用

}

Linux 上的落地（os_linux.go:180）：

r := clone(cloneFlags, stk, unsafe.Pointer(mp), unsafe.Pointer(mp.g0),
    unsafe.Pointer(abi.FuncPCABI0(mstart)))

2.6 新线程的入口：mstart ##

新 OS 线程从 mstart 进来：mstart0（proc.go:1660）→ mstart1（proc.go:1702）→ 先执行 mstartfn（这里是 mspinning，把自己标记为 spinning）→ acquirep(mp.nextp.ptr()) 接管 newm 时预留的那个 P → schedule()，永不返回，进入"取 G → 跑 G → 取 G"的大循环。

mstart1 里有一行很关键（proc.go:1715-1717），先记住它，后面讲 M 退出要用：

// Set up m.g0.sched as a label returning to just
// after the mstart1 call in mstart0 above, for use by goexit0 and mcall.
gp.sched.g = guintptr(unsafe.Pointer(gp))
gp.sched.pc = getcallerpc()   // 即 mstart0 里 mstart1 调用点的返回地址
gp.sched.sp = getcallersp()

2.7 一图总结创建路径 ##

go f()                          // 编译器 → runtime.newproc(f)
  └─ newproc (systemstack)
       ├─ newproc1:  gfget 复用G / malg 新建G → _Grunnable → 分配 goid
       ├─ runqput(next=true):  runnext → local[256] → (满了) runqputslow → global
       └─ wakep():  nmspinning==0 && 有idleP ?
            └─ startm(spinning=true)
                 ├─ mget() 有空闲M → notewakeup 唤醒（不建线程）
                 └─ 没有 → mReserveID → newm → newm1 → newosproc
                        └─ clone(mstart)   ← 新OS线程
                              └─ mstart1 → mspinning → acquirep(nextp) → schedule()

两个容易记错的点：

  1. newproc 本身从不直接建线程，它只负责入队 + 调 wakep；建不建线程的决策下放到 startm 的 mget() 分支。
  2. 热路径无锁：runqput 入 local 队列是无锁 CAS；只有真正要唤醒/创建线程时才拿 sched.lock。

三、决策依据：spinning 与"工作守恒" ##

为什么 wakep 要检查 sched.nmspinning？这是 Go 调度器最核心的设计，proc.go:33-100 顶部的大段注释专门讲它，我提炼如下。

什么是 spinning M：一个 M 在 findRunnable 里找遍了 local 队列、global 队列、netpoll 都没活，就进入"偷活"状态——从其他 P 的队列里随机偷 goroutine 来跑，此时它标记为 spinning（becomeSpinning，proc.go:927，计数 sched.nmspinning）。

为什么要保守：如果每提交一个工作就拉一个线程（注释里否决过的方案 3），会出现"线程刚被拉起来，活儿已经被别人抢走，又立刻睡回去"的抖动。所以策略是：

提交工作时，只要系统里还有一个 spinning 线程在找活，就不再拉新线程——反正马上有人会来拿。

怎么保证最终并行度：如果 spinning 线程找到了活、退出 spinning 状态（resetspinning，proc.go:3737），它必须再 wakep() 一次补一个名额，保证"工作提交侧不拉、消费侧补拉"这套守恒不破。这是经典的"delicate dance"（proc.go:3344 附近的注释），本质是两道 #StoreLoad 屏障之间的竞态处理。

spinning 线程数量上限：findRunnable 里 2*sched.nmspinning < gomaxprocs - sched.npidle（proc.go:3249），即最多一半的忙 P 可以有 spinning M，防止低并行度程序空转 CPU。

四、M 的复用：空闲池与 park/wakeup ##

新 M 跑完手头所有 goroutine 后怎么办？看 findRunnable 的末尾（proc.go:3322-3342）：

// return P and block
lock(&sched.lock)
...
if releasep() != pp {
    throw("findrunnable: wrong p")
}
now = pidleput(pp, now)     // ① 把 P 还回 sched.pidle 空闲池
unlock(&sched.lock)
...（delicate dance：再检查一遍有没有新工作）...
stopm()                     // ② 把自己挂起

stopm（proc.go:2766）：

lock(&sched.lock)
mput(gp.m)                  // ① 把自己放回 sched.midle 空闲 M 池（proc.go:6363）
unlock(&sched.lock)
mPark()                     // ② notesleep(&m.park) 睡在 park note 上
acquirep(gp.m.nextp.ptr())  // ③ 被唤醒后接管 startm 预留的 P
gp.m.nextp = 0

唤醒侧就是前面 startm 里的 notewakeup(&nmp.park)。

关键结论：空闲 M 只 park、不销毁，也没有"空闲超时回收"机制。 线程数量只增不减，水位线 = 历史并发峰值。这也是为什么压测结束后进程的线程数不会降下来——它们在池子里睡觉，等下一波流量直接复用。

五、M 的退出：什么时候线程真的消失 ##

既然空闲 M 不销毁，那 M 到底什么时候退出？答案是：正常 worker M 永不主动退出，只有少数特殊路径会退出。

5.1 为什么正常 worker M 永不退出 ##

goroutine 执行完（或调用 runtime.Goexit）后走 goexit0（proc.go:4179）：

func goexit0(gp *g) {
    gdestroy(gp)     // 清理、回收 G 到 gFree 池
    schedule()       // ★ 直接回到调度器，继续跑下一个 G，不是退出线程！
}

M 的大循环是 schedule() → 跑 G → goexit0 → schedule() → ...，除非走下面的特殊路径，否则 schedule() 永不返回，线程永不退出。

5.2 真正会退出 M 的三条路径 ##

① locked M：goroutine 锁了线程，退出时把 M 一起带走（最常见）

gdestroy 里（proc.go:4229-4243）：

if locked {
    // The goroutine may have locked this thread because
    // it put it in an unusual kernel state. Kill it
    // rather than returning it to the thread pool.
    if GOOS != "plan9" {
        gogo(&mp.g0.sched)   // ★ 回到 mstart0，走 mexit
    }
}

原因注释写得很清楚：runtime.LockOSThread 的 goroutine 可能把线程的内核状态搞得很"奇怪"（比如调过 C 的线程 API），这种线程不适合还给池子复用，直接杀掉。gogo(&mp.g0.sched) 用的是 2.6 节里 mstart1 预留的 g0.sched——一跳就回到 mstart0 中 mstart1 调用之后，于是 mstart0 返回，调用 mexit（proc.go:1695）。

② m0：main 线程，楔死（wedge）而不是退出

mexit 开头特判（proc.go:1778-1797）：main 线程不能真正退出（Linux 上会变成不可 wait 的 zombie 进程），所以把 P 交出去后 mPark() 永久睡死。

③ 进程退出：所有线程随进程消亡，无需单独处理。

另外两个容易被误认为"退出"的路径，其实都不退出：

  • syscall 返回后 P 被抢走：exitsyscall0（proc.go:4704）把 G 丢进 global 队列（globrunqput），自己 stopm() 进池睡觉，继续复用。
  • cgo 回调的 extra M：needm 从 extra 池借、dropm（proc.go:2363）归还（putExtraM，proc.go:2570），也不销毁，池化复用；extra M 池在 cgo 程序启动时由 newextram（proc.go:2266）预建。

5.3 mexit 内部流程（proc.go:1775） ##

func mexit(osStack bool) {
    ...m0 特判 wedge...
    sigblock(true); unminit()
    stackfree(mp.gsignal.stack)      // ① 释放信号栈

    // ② 从 allm 全局链表中摘除自己
    lock(&sched.lock)
    for pprev := &allm; *pprev != nil; pprev = &(*pprev).alllink {
        if *pprev == mp { *pprev = mp.alllink; goto found }
    }
found:
    // ③ 挂到 sched.freem 延迟回收链表（freeWait=freeMWait）
    mp.freeWait.Store(freeMWait)
    mp.freelink = sched.freem
    sched.freem = mp
    unlock(&sched.lock)

    handoffp(releasep())             // ④ 交还 P（可能因此 startm 拉新 M 顶班）

    lock(&sched.lock)
    sched.nmfreed++
    checkdead()                      // ⑤ 死锁检测
    unlock(&sched.lock)
    ...
    exitThread()                     // ⑥ OS 线程真正退出
}

注意第 ③ 步的延迟回收设计：M 不能立即释放自己 g0 栈（自己还在栈上跑着呢），所以先挂到 sched.freem 链表、标记 freeWait = freeMWait，等下一次 allocm 创建新 M 时（proc.go:2072-2106）再真正 stackfree(g0.stack) 并释放 m 结构体。allm 上已经看不到这个 M 了，所以对调度器来说它已经"死了"。

5.4 死锁检测：checkdead ##

checkdead（proc.go:5857 附近）在 mexit、stopm、sysmon 等路径都会调用：如果所有 M 都退出/挂起、所有 P 都 idle、还有 runnable 的 G，就 panic：

fatal error: all goroutines are asleep - deadlock!

mexit 里特别强调要先 handoffp 再 checkdead，因为 handoffp 可能已经拉起了新 M 来接手释放的 P 上的工作（proc.go:1848-1850 注释）。

5.5 上限 ##

newm 前还有个数量上限：sched.maxmcount = 10000（proc.go:777），checkmcount（proc.go:854）超限直接 throw "runtime: program exceeds 10000-thread limit"。

六、local 还是 global：入队与取队规则汇总 ##

入队（谁负责放）：

来源去向代码
go 语句新 G本 P runnext → local[256] →（满）globalrunqput(next=true)，proc.go:6635
channel/锁/netpoll 唤醒（goready）唤醒者 P runnext → local →（满）globalready → runqput(next=true)，proc.go:411/952
netpoll 批量唤醒无当前 P 时进 global，有则当前 P localinjectglist，proc.go:3761
从 syscall 返回但 P 被抢直接 globalexitsyscall0 → globrunqput，proc.go:4730

取队（谁来取、按什么顺序）——findRunnable（proc.go:3139）：

  1. GC worker / trace reader 等特殊 G（proc.go:3163-3183）；
  2. 每 61 个 schedtick 强制看一次 global 队列（proc.go:3188）——公平性，防止两个 G 互相 go 把 local 占死、饿死 global；
  3. 本 P runnext → local（runqget，proc.go:3208）；
  4. global 队列（proc.go:3213，globrunqget 一次取 runqsize/gomaxprocs + 1 个摊到各 P，proc.go:6435）；
  5. netpoll 非阻塞轮询（proc.go:3229）；
  6. 偷活：从随机 P 偷 local 队列一半（stealWork/runqsteal，proc.go:6868）——这就是 spinning 线程干的事；
  7. 全空 → 放弃 P（pidleput），阻塞在 netpoll 等事件，或 stopm 进空闲池睡觉。

七、HTTP 服务全流程复盘 ##

以 net/http 的 accept 循环为例（src/net/http/server.go:3254）：

for {
    rw, err := l.Accept()      // netpoll 阻塞，无连接时挂起
    ...
    go c.serve(connCtx)        // server.go:3285，每连接一个 goroutine
}

0 请求：m0 + sysmon，8 个 P 全 idle。accept goroutine 阻塞在 Accept 的 netpoll 上。

第 1 个请求：连接到达 → netpoll 唤醒（netpollgoready，netpoll.go:538 → goready → ready(next=true)）→ accept goroutine 进 m0 所在 P 的 runnext → m0 自己立刻执行，不需要新 M。go c.serve(connCtx) 创建连接处理 G → 进当前 P 的 runnext → 立刻跑。

请求量变大：每连接一个 G，但绝大多数时间这些 G 都阻塞在 socket 读写上。阻塞 → gopark → M 释放 P → handoffp（proc.go:2905）。关键分支：

  • P 上还有 runnable G（local 非空）→ startm(pp) → 空闲池有 M 就唤醒，没有就 newm 建新线程；
  • P 上没活了 → P 进 idle 池，M 去 findRunnable 偷活或睡觉。

线程数涨上去的典型节奏：第 1 个 M 阻塞在 I/O → 它的 P 被 handoffp 交给新 M（第 2 条线程）→ 又阻塞 → 第 3 条……直到每个 P 都有一个 M 在跑。之后即使再创建 goroutine，newproc 的 wakep() 会发现要么没有 idle P、要么已有 spinning M，不再创建线程，G 只是排队。有些 syscall 卡太久（> 20µs），sysmon 的 retake（proc.go:6136 附近）会把 P 抢回来交给别人，原 M 从 syscall 返回后 exitsyscall0 排队睡觉。

请求降下来：M 在 findRunnable 找不到活 → stopm 进空闲池（sched.nmidle 上涨）——线程不销毁，下波流量直接复用。这就是 Go 服务"线程数 = 历史峰值"现象的由来。

八、如何观察：GODEBUG=schedtrace ##

用 GODEBUG=schedtrace=1000,scheddetail=1 跑服务，每 1s 打印一行（proc.go:6241）：

SCHED 1000ms: gomaxprocs=8 idleprocs=6 threads=5 spinningthreads=1 idlethreads=1 runqueue=0
字段含义对应源码
threads=当前 M 总数（mcount）mcount()
idleprocs=idle P 数sched.npidle
spinningthreads=在偷活的 M 数sched.nmspinning
idlethreads=在空闲池睡觉的 M 数sched.nmidle
runqueue=global 队列长度sched.runqsize

配合 scheddetail=1 还能看到每个 P 的 runqsize（local 队列长度）。观察请求量从 0 涨到峰值再回落的全程，你会发现 threads 只增不减、idlethreads 先涨后稳——这就是本文讲的机制在真实进程里的样子。

九、小结 ##

  1. P 预创建、M 惰性创建：启动时只有 m0（+sysmon），P 全量就位但全 idle。
  2. M 创建的充要条件链：有新工作（newproc/ready/handoffp）→ wakep 判定"有 idle P 且无 spinning M"→ startm 判定"空闲 M 池为空"→ newm 建线程。本质是惰性 + 保守：能复用绝不新建，有线程在找活（spinning）就绝不添乱。
  3. M 只增不减：空闲 M 在 stopm/mPark 里睡觉等 notewakeup，没有超时回收；线程数水位 = 历史并发峰值（上限 10000）。
  4. M 退出的三种真实路径：locked M 随锁定 goroutine 退出（gogo → mexit）；m0 楔死；进程退出。cgo extra M 与 syscall 滞留 M 都不退出，池化复用。
  5. local vs global：go 语句默认进本 P runnext → local 256 格；满了才溢出 global；取时 local 优先、每 61 tick 掺一次 global 保证公平、空了才偷别人的 local。
