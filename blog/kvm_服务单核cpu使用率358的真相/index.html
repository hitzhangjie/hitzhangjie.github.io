kvm(3)： 溯源CPU 占用率为何飙升到 350%

Posted 2026-07-25 00:00 +0800 by ZhangJie ‐ 1 min read

分享:  

背景 ##

上一篇文章 中，我们通过逐层排查，最终定位到同母机上另一台子机的 Split Lock 是导致业务 CPU 飙高的根因。腾讯云侧确认后将我们的子机迁移到其他正常母机，问题恢复。

但排查过程中还有一个现象始终令人困惑：单核 CPU 占用率达到了 358%+——理论上即使满载，单核算 CPU 使用率也不可能超过 100%。Split Lock 到底做了什么，能让监控数据出现如此反常识的数值？

本文将顺着 Split Lock → 内存总线锁 → vCPU 调度延迟 → IRQ 积压注入 → missed timer ticks 补偿这条链路，逐一分析 CPU 占用率升高的原因，以及突破 100% 的机制。

splitlock，这会导致什么问题呢? ##

有哪些性能方面的影响? ##

  • 触发splitlock的子机，加解锁内存总线，自身性能会下降，它内部也有其他访存操作；
  • 其他子机中的访存操作，CPU也会等待内存总线就绪，也会引入访存延迟；
  • 子机执行过程中本来可能在合适的时候进行切换，让出CPU给其他子机使用，但是现在CPU更可能被占着等内存总线就绪；
  • 从整体来看，可能会给其他子机的调度带来不可避免的调度延迟，尤其是再考虑到云服务商一般都存在轻微的超卖的情况； 所以，很好理解，splitlock会给所有自己带来调度延迟，并且导致实际处理能力下降的问题。这根我们前期观测到的服务处理能力下降，业务侧请求处理耗时增加，也一致。

为什么CPU占用率升高呢？ ##

  • 子机被调度到目标CPU上执行，自打linux 2.6引入CFS调度器以后，进程运行时间的统计就从 “timer tick采样累计执行时间” 改成了 “调度器切换时更新累计运行时间片” 的方式了；
  • 自己被调度到目标CPU上执行，遇到内存总线锁，CPU干等，干等的这段时间也会计入运行时间，如果子机中任务在运行时间片内CPU全部在等内存总线释放，干等，那就是接近100%使用率；
  • 在调度延迟期间，如果irq到达，会首先交给母机处理，母机再转给kvm模块，等后续vm被调度时，kvm再注入这些irq到vm内部，vm内部再处理，irq多自然也会推高CPU占用；

    我们也确实看到了问题时间点大量irq情况。

为什么CPU占用率超过100%呢？ ##

  • 如果短时间内涌入大量irq，应该会推高瞬时CPU占用率。正常情况下vm调度没有延迟，不会攒这么多中断一次性注入处理。注入中断的过程，称之为irq catchup，为了让vm跟上并及时处理；
  • 如果上述irq中包含了一些定时器中断，timer ticks，kvm只会注入一个irq给vm，vm判断这个irq实际上表示错过了多个timer ticks，不同版本内核在据此补偿进程运行时间时，行为有差异。
    • periodic：补偿多次。我实际测试 3.10版本内核，并且highres=off nohz=off 时通过bpf跟踪一个irq处理，确实会出现补偿多次的情况；
    • oneshot模式：只补偿一次。即使是3.10内核，在不显示传递上述参数的情况下，也不会补偿多次，因为走的是oneshot模式。更不用说新版本内核了，我们线上是5.1内核。rhel7是3.10，rhel8是5.15； 这里补偿的时间确实可能导致CPU单核使用率超过100%的，实际periodic模式下，这个非常容易复现出来。
  • 如果虚拟化时kvm启动实例时 -kvm-steal-time，就没有打算同步这些被hypervisor（kvm）调度偷走的时间，那么可能不容易修正运行时间。 比如上述irq catchup过程导致的进程运行时间增加，steal time本来还可以修正。 但是云服务商为了不让业务侧看到有超卖现象，可能会不同步这个steal time（共享内存机制），这样算出来就超过100%了。
