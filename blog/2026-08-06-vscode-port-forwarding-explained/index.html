VS Code 端口转发（Port Forwarding）原理解析

Posted 2026-08-06 11:04 +0800 by ZhangJie ‐ 3 min read

分享:  

如果你用过 VS Code 的 Remote 系列扩展（Remote-SSH / Dev Containers / Tunnels / Codespaces），大概率打开过底部那个 Ports 面板：

  • 它能把远端机器上某个端口的服务，「搬」到你本地的 127.0.0.1 上
  • 你在本地浏览器访问 http://localhost:9876，请求其实被偷偷送到了远端
  • 一些端口不用手动加，VS Code 会自动嗅探并帮你转发（标为 Auto Forwarded）

用起来很顺，但背后的实现涉及控制信道、端口嗅探、本地代理三层协作。下面把这套机制讲清楚。

1. 整体架构：三端协作 ##

端口转发的本质，是在你已经建立的远端连接（SSH 会话 / WebSocket 隧道）之上，再「搭便车」开一条 TCP 流。整体结构：

┌──────────────┐        控制信道 (RPC/WS)        ┌──────────────────┐
│  VS Code UI  │ ◀────────────────────────────▶ │  Local Proxy /   │
│  (本地客户端) │                                 │  Tunnel Client   │
└──────────────┘                                 └──────────┬────────┘
                                                            │
                                                    本地监听 127.0.0.1
                                                    （你访问的入口）
                                                            │
                                                    ═══ 安全隧道 ═══
                                                            │
                                               ┌────────────▼─────────────┐
                                               │  Remote Server           │
                                               │  (code-server / sshd)    │
                                               │  + Port Forwarding Mgr   │
                                               └──────────────────────────┘

关键认知：你在本地访问 127.0.0.1:9876 时，请求不会直达远端服务进程。它先到本地 VS Code 的代理层，被封装进一条已存在的控制信道，由远端 side 拆包后再转发给真正的服务。这条控制信道本身就是 SSH 连接或 WebSocket 隧道，不需要为端口转发额外打洞。

2. 两种底层实现方式 ##

2.1 基于 SSH 的 Remote-SSH ##

走标准 OpenSSH 的 Local Port Forwarding，原理跟命令行 -L 一样：

ssh -L 9876:127.0.0.1:9876 user@host

VS Code 内部就是动态生成并管理这些 -L 参数。code-server 进程在远端监听 9876，SSH 客户端在本地开 127.0.0.1:9876，数据通过加密的 SSH 通道双向透传。

优点：协议成熟，零额外依赖，安全性由 SSH 保证。

2.2 基于 WebSocket 多路复用（Dev Containers / Tunnels / Codespaces） ##

没有 SSH 时（比如 Codespaces、自建 Tunnels、WSL），VS Code 自己实现了一套：

  1. 本地：vscode-cli 或编辑器内的 tunnel client 启动一个出站的 WebSocket 连接到 relay（微软的 global.rel.tunnel.services.visualstudio.com，或自建 relay）
  2. 远端：./code-server 或 dev container 里的 sidecar 也连接到同一个 relay
  3. 两端通过同一条 WebSocket传输多路复用的 RPC 帧（multiplexer，类似 yamux / smux）
  4. 端口转发就是在这个 multiplexer 上「开一条流」——你本地的 127.0.0.1:9876 流量被打包成帧，relay 透传，远端拆包后转发给真正的服务

优点：能穿透 NAT/防火墙，无需开放入站端口，体验比 SSH 更「无感」。

3. Ports 面板每列的精确含义 ##

列含义
Port远端服务进程实际监听的端口号（注意不是本地的，详见第 5 节）
Forwarded Address你本地访问时用的地址（localhost:9876 是本机 loopback，只有本机可访问）
Running Process远端在监听该端口的进程（如 ./df-releaseit-web），可点开看进程详情
Origin转发来源：User Forwarded = 你手动 Add Port 加的；Auto Forwarded = 远端自动嗅探到新进程开端口后通知过来的
小圆点蓝点 = 已建立活跃 TCP 连接；空心圈 = 转发配置存在但当前无流量/未连通

4. Auto Forwarded 是怎么嗅探出来的 ##

这是远端 code-server 里的 Port Forwarding Manager（源码大致在 vscode/src/vs/workbench/contrib/remote/browser/portForwarding.ts 附近）干的活：

  1. 周期性扫描远端的 tcp / tcp6 socket 表（读 /proc/net/tcp 或调用 ss / lsof）
  2. 跟「用户明确拒绝转发」的端口白/黑名单对比
  3. 对新出现的、非 system 端口、且属于当前 workspace 相关进程的端口，按规则决定是否自动转发（规则在 settings.json 里可配：remote.autoForwardPorts、remote.portsAttributes）
  4. 通过控制信道的 RPC 把「建议自动转发」的端口推给本地 UI，UI 渲染成 Auto Forwarded 那行

也就是说，自动转发不是本地客户端在嗅探，而是远端 side 嗅探完通过控制信道推过来的——这是为什么你即便关掉本地 VS Code 重开，远端服务一旦重启监听新端口，本地 UI 仍然能感知到。

5. Port 列与 Forwarded Address 列：最易混淆的一对 ##

Port 这一列其实有点反直觉，单独展开说。

Port 显示的是远端机器上服务进程实际监听的端口号，不是你本地访问的端口。但 VS Code 默认会把本地端口设成跟远端一样，所以面板上看起来像同一个数字，很容易让人误以为它就是本地端口。

真实关系：

本地访问:    127.0.0.1:<本地端口>      ← Forwarded Address 这一列
                          │
                    ═══ 隧道 ═══
                          │
远端转发到:  127.0.0.1:<远端端口>      ← Port 这一列
                          │
                    命中服务进程

5.1 两行对比 ##

行Port（远端）Forwarded Address（本地）含义
第 1 行9876localhost:9876远端服务监听 9876；本地也用 9876 接入
第 2 行9999127.0.0.1:9999远端服务监听 9999；本地也用 9999 接入

两个本地地址写法不同（localhost vs 127.0.0.1）只是显示风格差异，本质都是本机 loopback。只有本机能访问，外部机器访问不到——这是端口转发的安全默认值。

5.2 本地端口 ≠ 远端端口的情况 ##

如果本地 9876 被占用，VS Code 会自动选一个空闲本地端口（比如 54321）映射到远端 9876。这时两列会变成：

Port: 9876                          ← 远端
Forwarded Address: localhost:54321  ← 本地

你访问时必须用 54321，而不是 9876。真正决定你在本地浏览器输什么 URL 的是 Forwarded Address 列，不是 Port 列。

6. 三个常见误区 ##

  1. 以为 Port 是本地端口 → 错，是远端的
  2. 以为两列永远相同 → 错，本地端口冲突时会变
  3. 以为别的机器能通过你的 IP 访问 → 错，默认只绑 loopback，要对外暴露得改 127.0.0.1 为 0.0.0.0（在端口上右键 → Change Visibility → Private/Public）

7. 实用配置建议 ##

在 settings.json 里几个常用项：

{
  // 关闭自动转发（如果你嫌吵）
  "remote.autoForwardPorts": false,

  // 自动转发的源（local 优先嗅探本地启动的进程）
  "remote.autoForwardPortsSource": "hybrid",

  // 指定端口的可见性/协议（按端口配属性）
  "remote.portsAttributes": {
    "9876": {
      "label": "releaseit-web",
      "onAutoForward": "notify",
      "protocol": "http"
    }
  }
}

如果想看协议层细节：

  • VS Code 仓库的 src/vs/platform/remote/ 和 src/vs/workbench/contrib/remote/，搜 port forwarding 关键字
  • 官方文档：https://code.visualstudio.com/docs/remote/ssh#_forwarding-a-port-creating-and-using-tunnels

总结 ##

VS Code 的端口转发，本质是复用已建立的远端连接，在其上搭便车开 TCP 流。三点值得记住：

  1. 协议层：Remote-SSH 走 SSH -L；Dev Containers / Tunnels / Codespaces 走 WebSocket 多路复用
  2. 面板语义：Port 是远端端口，Forwarded Address 是本地入口；本地端口冲突时两者会不同
  3. 自动嗅探：远端 side 扫 socket 表，通过控制信道推给本地 UI，所以重连后仍能感知远端新进程

下次遇到「端口转发不工作」「自动转发太吵」「想对外暴露」这类问题，按这三层对号入座去排查即可。
