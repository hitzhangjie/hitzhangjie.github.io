SigNoz 整体架构：一个基于 OpenTelemetry 的开源可观测性平台

Posted 2026-07-29 12:00 +0800 by ZhangJie ‐ 3 min read

分享:  

背景 #

上一篇文章 里我们系统梳理了 OpenTelemetry 的核心概念。OTel 解决的是"数据怎么采、怎么传"的问题，但它不解决"数据怎么存、怎么查、怎么告警"的问题。你需要一个后端。

后端的选择其实不少：Jaeger（专注 Tracing）、Prometheus + Grafana（专注 Metrics）、ELK（专注 Logging），更不用提 Datadog、New Relic 这些商业 SaaS。但三件套拼在一起有几个痛点：

  1. 数据孤岛：Traces 在 Jaeger、Metrics 在 Prometheus、Logs 在 Elasticsearch，查问题时要在三套系统间跳来跳去。
  2. 基础设施碎片化：每套系统有自己的部署、配置、升级节奏，运维成本随套数线性增长。
  3. 告警能力割裂：没法在一个地方同时基于 Metrics 阈值和 Trace 延迟来定义告警规则。

SigNoz 试图用一个统一平台解决这些痛点。它是 CNCF 生态下的开源项目，原生基于 OpenTelemetry，将三大信号的存储、查询、可视化和告警整合到一起。下面拆解它的整体架构。

下面逐层拆解每个组件。

核心组件拆解 #

Query Service（SigNoz Server） ##

这是 SigNoz 的"大脑"，一个 Go 语言编写的后端服务，容器镜像 signoz/signoz。它承担了：

  • 查询引擎：接收前端请求，翻译成 ClickHouse SQL，聚合结果返回。由于 ClickHouse 是列式存储，对于时序聚合和全文检索都很擅长，一个引擎同时搞定了 Traces 的搜索、Metrics 的聚合和 Logs 的全文检索。
  • 告警引擎：定时评估告警规则（基于 PromQL 风格的查询或者 ClickHouse 直查），触发后通知 Alert Manager 下发。规则存储在 SQLite 中，规则评估的查询打在 ClickHouse 上。
  • 用户与权限管理：用户信息、团队信息存储在 SQLite 中。
  • Web UI 服务：内置的前端静态资源服务，默认监听 8080。

一个重要的部署细节：SigNoz Server 需要知道 ClickHouse 的连接地址（通过环境变量 SIGNOZ_TELEMETRYSTORE_CLICKHOUSE_DSN=tcp://clickhouse:9000）和 SQLite 的路径。它启动后做健康检查，暴露 /api/v1/health 端点。

OpenTelemetry Collector ##

这里的 Collector 使用了 SigNoz 定制版镜像 signoz/signoz-otel-collector，而不是原版 otel/opentelemetry-collector-contrib。这是因为 SigNoz 在 Collector 中加入了：

  • ClickHouse Exporter：原版 Collector 没有直接写 ClickHouse 的 Exporter，SigNoz 自己实现了一个，让 Collector 直接消费 OTLP 数据写入 ClickHouse。这是 SigNoz 架构中最关键的定制点。
  • OpAMP 支持：通过 --manager-config 指定一个 OpAMP 管理配置，支持远程动态更新 Collector 配置。在 SigNoz Cloud 场景下，这可以让平台侧统一管理所有 Collector 实例。
  • schematic 功能开关：如 --feature-gates=-pkg.translator.prometheus.NormalizeName，关闭 Prometheus 指标名的标准化（保留原始名字，避免与用户预期不符）。

Collector 打开两个标准 OTLP 端口：4317（gRPC）和 4318（HTTP）。业务应用通过这两个端口上报遥测数据。

Collector 依赖 ClickHouse 的健康状态和 schema-migrator 的同步完成，因为一启动就要往数据库写数据，如果表还没建好就会出错。

ClickHouse：核心存储 ##

ClickHouse 是 SigNoz 存储选型的关键决策。为什么选它？

  • 列式存储：Traces 和 Logs 查询通常只需要部分字段（如 service_name、duration、status_code），列式存储可以跳过无关列，查询更快。
  • 高写入吞吐：MergeTree 引擎支持每秒数百万行的写入，能扛住海量 Span 和 Metric 数据点的摄入。
  • 压缩率高：列式存储天然适合压缩，实际压缩比通常在 5-10 倍，大幅降低存储成本。
  • SQL 接口：不需要学习新的查询语言，团队学习成本低。

ClickHouse 在 SigNoz 中存储了 Traces、Metrics 和 Logs。每类数据有自己的数据库和表族，表结构由 Schema Migrator 管理。

ClickHouse 可以单机部署（我们讨论的 docker-compose 即单机模式），也可以部署为集群，依赖 Zookeeper 做副本协调。

SQLite：元数据存储 ##

SQLite 存储的是"关于数据的数据"——告警规则定义、通知渠道配置、用户信息、Dashboards 元数据等。这些数据量小、访问频率低、不需要分布式，SQLite 足够。

SQLite 文件通过 Docker Volume 持久化，即使容器重启，配置也不会丢失。选择 SQLite 而不用 etcd 或 MySQL，降低了小规模部署的运维成本。

Zookeeper：集群协调 ##

单机 ClickHouse 不需要 Zookeeper，但一旦扩展到 ClickHouse 集群（多分片、多副本），就需要 Zookeeper 来协调副本之间的数据同步、选主等操作。

SigNoz 默认在 docker-compose 中部署了 Zookeeper，主要是为 ClickHouse 集群模式预留。单机部署时它的存在感很低，但它是架构中的一个必要组件——当 ClickHouse 配置了 cluster.xml 中定义了复制表时，就需要 Zookeeper 来协调。

Schema Migrator ##

这是 SigNoz 中一个容易被忽略但很关键的组件。随着版本迭代，ClickHouse 的表结构会变化——加字段、加索引、调整分区策略等。Schema Migrator 负责执行这些 DDL 变更。

它分两种模式：

  • sync（同步迁移）：阻塞式执行关键的表结构变更，必须成功后才允许 Signoz Server 和 Collector 启动。因为如果 Collector 开始往表里写数据但表结构不对，数据就会丢失或损坏。
  • async（异步迁移）：后台执行非关键的迁移，比如物化视图的更新。不影响服务启动。

两个 migrator 的 restart: on-failure 配置保证了迁移失败会自动重试——这是必要的，因为 ClickHouse 可能还没完全就绪。

数据流全景 #

把上文串起来，一条 Trace 数据的完整生命周期是这样的：

1. 应用 (OTel SDK) 创建 Span
2. 通过 OTLP/gRPC 发送到 Collector (:4317)
3. Collector 的 batch processor 攒够一批 Span
4. Collector 的 ClickHouse Exporter 将这批 Span 写入 ClickHouse
5. 用户在 SigNoz UI (:8080) 搜索 Trace
6. SigNoz Server 将查询翻译为 ClickHouse SQL
7. ClickHouse 返回结果，SigNoz Server 聚合后渲染为火焰图
8. 同时，Alert Manager 在后台轮询告警规则
9. 如果触发，通过配置的 Channel（Slack/Email/Webhook）发送通知

Metrics 和 Logs 的流程大致相同，唯一的区别是 ClickHouse 中存储的表不同，以及在 Collector 侧 Metric 数据会经过额外的聚合处理。

告警系统 #

SigNoz 的告警支持三种数据源：Metric-based、Log-based、Trace-based。

Metric-based 告警最常见：在某个 Dashboard 上定义一个阈值规则，如"5 分钟内 http_server_duration 的 P99 超过 500ms"。Log-based 告警可以做到"5 分钟内包含 OutOfMemoryError 的日志超过 10 条"。

告警通知通过 Channel 下发，SigNoz 支持：

Channel说明
Slack通过 Incoming Webhook 集成
EmailSMTP 发送
Webhook最通用的方式，发送 JSON Payload 到任意 HTTP Endpoint
Microsoft Teams通过 Teams Incoming Webhook
PagerDuty / OpsGenie对接 OnCall 平台

其中 Webhook 是最灵活的选择。它发送的 Payload 格式兼容 Prometheus AlertManager 的 Webhook 格式，包含 alerts 数组、status（firing/resolved）、commonLabels、commonAnnotations 等字段。你可以自己实现一个 HTTP 服务接收这些告警，然后按需路由、聚合、升级。

与其他方案对比 #

维度SigNozJaeger + Prometheus + GrafanaDatadog
Traces / Metrics / Logs统一平台，单 UI三套独立系统统一 SaaS
存储引擎ClickHouseCassandra/ES（Jaeger）, TSDB（Prometheus）自研
OpenTelemetry 原生是，CLBO（Cloud-Native Log-Based Observability）理念Prometheus 非 OTel 原生支持但不完全
告警内置，三大信号共享Grafana Alerting 为主内置
运维成本中等（docker-compose 或 K8s）高（三套系统各自运维）低（SaaS）
成本开源免费开源免费按数据量收费

SigNoz 的定位非常清晰：在开源自部署和商业 SaaS 之间找到一个平衡。它比"三件套拼凑"更统一，比 Datadog 更自主可控。

总结 #

SigNoz 的架构并不复杂，它的设计思路很务实：

  1. 采：复用 OTel Collector（做了 ClickHouse Exporter 定制）接收数据
  2. 存：ClickHouse 做核心存储（列式、高写入吞吐、压缩率高），SQLite 做元数据存储
  3. 查：Go 后端翻译前端查询为 ClickHouse SQL
  4. 告：内置规则引擎 + 多渠道通知

理解了这套架构，再去读它的 Docker Compose 配置，每个 service 的角色就会很清晰——这篇配置分析正是下一篇的内容。
