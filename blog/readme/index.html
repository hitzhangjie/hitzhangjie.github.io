Split Lock → CPU 计量失真复现 #

问题背景 ##

线上观察到 gopsutil 报告单核 CPU 使用率 350%+，理论上除以核数后不应超过 100%。 该异常与同母机另一台 VM 的 split-lock 问题时间点吻合。

假说 ##

Split-lock → 母机资源争抢 → 我们的 vCPU 被反复 deschedule/resume → guest 内核 timer catchup 补偿 → /proc/[pid]/stat 的进程 CPU 时间增量与 clock_gettime 墙钟增量失配 → 单核使用率计算破 100%。

文件说明 ##

文件说明
splitlock.cC 语言 split-lock 触发程序（跨 cache line 的 lock add）
main.goGo 语言 CPU 监控程序（复现 gopsutil 的计算逻辑）
DockerfileDocker 环境（演示用，不会复现 350% 异常）
vm-setup.shQEMU/KVM 完整复现脚本（需要真实 VM）
Makefile构建脚本

快速开始 ##

1. 本地编译运行（不触发 split-lock） ##

make all                          # 编译
./splitlock 2 &                   # 后台启动 split-lock（2 线程）
./cpumon $(pgrep splitlock)       # 监控其 CPU 使用率

在裸机/Docker 上，PerCore% 始终 ≤ 100%，这是正常基线。

2. Docker 运行 ##

make docker-build
make docker-run

Docker 共享宿主机内核，没有 vCPU 调度和 steal time 机制，无法复现 350% 异常。 这个 demo 仅用于验证工具的可用性。

3. QEMU/KVM 完整复现 ##

这是唯一能复现 350% 单核使用率的方案，因为需要：

  • 真实 KVM vCPU 调度
  • Steal time accounting
  • Guest kernel timer catchup
# 准备环境
./vm-setup.sh setup

# 启动两个 VM
./vm-setup.sh launch

# VM-A（port 2222）：运行 split-lock，制造母机资源争抢
ssh -i shared/id_ed25519 -p 2222 test@localhost
cd /var/lib/cloud/instance/scripts/
gcc -O2 -pthread -o splitlock splitlock.c
./splitlock 2

# VM-B（port 2223）：运行 cpumon，观察 CPU 计量异常
ssh -i shared/id_ed25519 -p 2223 test@localhost
cd /var/lib/cloud/instance/scripts/
go build -o cpumon main.go
./cpumon

# 观察输出中 PerCore% 是否超过 100%
# 同时在母机上：
sudo dmesg -w | grep -i 'split.lock'

预期结果 ##

Docker / 裸机: PerCore% 稳定在 0-100%，不会出现异常。

VM + split-lock 场景: 如下条件满足时可能出现 PerCore% > 100%：

  1. 母机 split-lock 检测已关闭（split_lock_mitigation=0），否则 guest 内 splitlock 进程会收 SIGBUS
  2. split-lock 线程数 ≥ VM 的 vCPU 数，确保母机资源争抢
  3. 母机上还有其他 VM（或宿主机进程）也在竞争 CPU

注意：即使条件满足，350% 这种极端值也不是每次都能复现。它与母机当时的调度状态、timer catchup 的时机有关，是一个概率性问题。这也解释了为什么当时子机内 atop 看不到（分钟粒度平均掉了尖峰）。

字段说明 ##

cpumon 输出的关键字段：

字段含义正常范围
ProcCPU%进程总 CPU 使用率可超过 100%（多线程）
PerCore%单核平均 CPU 使用率应 ≤ 100%，>100% = 异常
SysUser%系统态 user 时间占比0-100%
SysSteal%Steal time 占比通常 < 5%，高值表示 VM 资源争抢
SysTotal%系统总非空闲 CPU 占比0-100%

为什么 Docker 复现不了 ##

┌─────────────────────────────────────────┐
│ Docker Container                        │
│  ├── splitlock (C)                      │
│  ├── cpumon (Go)                        │
│  └── /proc/stat ← 这是 HOST 的 /proc!   │
│      没有 steal time 字段实际值           │
│      没有 vCPU 调度                       │
│      没有 kvm-clock                       │
└─────────────────────────────────────────┘
             │
    ┌────────┴────────┐
    │  Host Kernel    │ ← 共享内核，无 VM 层
    └─────────────────┘

┌────────────────┐  ┌────────────────┐
│ VM-A           │  │ VM-B           │
│ ┌────────────┐ │  │ ┌────────────┐ │
│ │ splitlock  │ │  │ │ cpumon     │ │
│ │ (C program)│ │  │ │ (Go)       │ │
│ └────────────┘ │  │ └────────────┘ │
│       │        │  │       │        │
│  guest kernel  │  │  guest kernel  │
│       │        │  │       │        │
│   /proc/stat ← │  │   /proc/stat   │
│   独立记账     │  │   含 steal time │
└───────┬────────┘  └───────┬────────┘
        │                   │
   ┌────┴───────────────────┴────┐
   │  QEMU/KVM + Host Kernel     │
   │  vCPU 线程调度               │
   │  steal time 更新             │
   │  时间补偿 (timer catchup)    │
   └─────────────────────────────┘

关键差异：VM 有 guest kernel 自己的 /proc/stat 记账 + hypervisor 的 steal time 注入 + vCPU 调度导致的 timer catchup。Docker 三者都没有。
