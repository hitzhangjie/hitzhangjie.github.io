Linux load average 到底在算什么？

Posted 2024-06-18 00:00 +0800 by ZhangJie ‐ 2 min read

分享:  

uptime 或者 top 中显示的 load average 到底统计的是什么东西，误解不少。

最常见的说法是"CPU 队列长度"或者"系统忙的程度"。这些说法不准确——load average 算的不是所有进程，而是 R 状态 + D 状态 的进程数，按指数移动平均平滑后的值。

load average 算了什么 ##

Linux 内核里有一个全局数组 avenrun[3]，分别存 1 分钟、5 分钟、15 分钟的 load average。每次时钟中断或者调度事件触发时，内核统计当前处于 TASK_RUNNING（R 状态）和 TASK_UNINTERRUPTIBLE（D 状态）的进程数，然后做指数平滑更新 avenrun。

R 状态包括正在 CPU 上跑的和在就绪队列里等 CPU 的。D 状态就窄得多，只有不可中断睡眠。

superuser 上有个回答总结得很清楚，load average 考虑三类进程：

  1. Actively running on a CPU —— 正在用 CPU
  2. Runnable but waiting for a CPU —— 等 CPU
  3. Sleeping: waiting for I/O —— 等磁盘 I/O

第三条说 sleeping，但实际只指 D 状态，不是所有睡眠都算。

为什么 D 状态要算进去 ##

这个问题是关键。S 状态（可中断睡眠）的进程占了系统的绝大多数，为什么不算？

因为 S 状态等的东西没有竞争性。

一个 bash 挂在那等你敲命令，等一天也不跟谁抢资源。1000 个 nginx worker 在 epoll_wait 上等连接，TCP 来了谁拿谁处理，互相之间没有任何争抢。sleep 3600 就更不用说了，定时器到了自然醒。这些进程本质上是空闲的。

D 状态不一样。D 状态的进程在等的是有限的硬件资源——磁盘 I/O 带宽。一块盘能同时处理的并发请求就那么多，进程在 D 状态就是在排队。这和 R 状态进程排 CPU 的队，本质上是同一件事：在抢有限的硬件。

所以 load average 的设计直觉很简单：有 N 个进程在争抢 CPU 或者磁盘 I/O，那系统就是 loaded 了 N 个单位。S 状态不在这个范畴里。

D 状态的"不可中断"是什么意思 ##

D 状态全称 TASK_UNINTERRUPTIBLE。这个词容易让人误解，澄清两点。

第一，“uninterruptible"指的是不能被**信号（signal）**唤醒。连 SIGKILL 都不行——kill -9 一个 D 状态的进程，信号挂到 pending 队列，进程不会消失，等它从 D 切回 R/S 后才处理。

只有内核有能力扭转它的状态，在此之前，谁也不能让它被调度器调度。了解过进程创建过程的可能会联想起来，进程创建过程中也有这么一个阶段，在准备好之前，谁也不能调度它。

第二，硬件中断完全不受影响。硬件中断不跟进程绑定——CPU 收到中断后直接跳到内核的中断处理程序，跟当前跑的是谁没关系。I/O 完成后正是靠硬件中断通知内核，内核再把那个 D 状态进程唤醒到 R。

ps: 这也解释了为什么有时候磁盘出问题，kill -9 都杀不掉进程——进程卡在 D 状态等 I/O，I/O 回不来，信号就没机会处理。

D 状态确实不参与调度——不在就绪队列里，不会被调度器选中。但它被计入 load average。这也是很多人觉得 load 指标奇怪的地方：一个什么都做不了、连信号都接不了的进程，占据了一个 load 单位。

这个设计的问题 ##

load average 诞生很早，那时候系统结构简单。放现在的环境，问题就凸显出来了。

D 状态太粗糙。等一块 USB 2.0 外接盘和等 NVMe SSD 的进程，贡献的 load 是一样的 1，但实际的 I/O 压力差了上百倍。load 数字本身看不出 I/O 有多"重”。

D 状态不一定是 I/O。有些内核路径会让进程进入 D 状态，跟磁盘 I/O 没有直接关系。比如等内存回收（direct reclaim）完成，或者等内核 mutex。这些场景下 load 飙高，但 CPU 和磁盘都可能很闲——你盯着 top 看会觉得很困惑。

压力失真。要命的是 D 状态的进程不会被抢占，也不能被迁移到别的 CPU 上去跑。如果大量进程因为同一个内核锁或者 vhost 事件被阻塞在 D 状态，load 数字可能飙到几十甚至上百。比如之前写的 KVM 场景里，单核 CPU 利用率 358%，load 高得吓人，但根因不是 CPU 不够用，而是 vhost 的事件处理阻塞了大量进程。

怎么用 load average ##

尽管有这些问题，load average 还是能用。

对于单核系统，load 的数字基本等于 CPU 利用率：0.25 就是 25% 在用，1.0 就是 CPU 跑满了，大于 1.0 就是在排队了。多核系统把数字除以核心数，4 核机器上 load 4.0 就是刚好跑满。

快速判断的口诀：

  • load 高 + CPU 使用率也高 → 正常，计算密集，该加机器就加机器
  • load 高 + CPU 使用率低 → 大概率是 I/O 瓶颈，进程在 D 状态排队。看 iowait，看 iotop，看是哪个盘在拖后腿

ps aux 里 D 状态进程可以直接看到，状态列显示 D。vmstat 1 里面的 b 列是阻塞在 I/O 上的进程数，也能辅助判断。

还有一个场景需要警惕：load 突然为 0。不要高兴太早，这有可能不是系统闲下来了，而是进程调度出了 bug，统计不到 R/D 状态的进程了。不过这种情况很罕见。

更准确的替代：PSI ##

2018 年 Facebook 往内核里贡献了 Pressure Stall Information（PSI），暴露在 /proc/pressure/ 下：

$ cat /proc/pressure/cpu
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
$ cat /proc/pressure/io
some avg10=0.00 avg60=0.00 avg300=0.00 total=0
full avg10=0.00 avg60=0.00 avg300=0.00 total=0
$ cat /proc/pressure/memory
some avg10=0.20 avg60=0.15 avg300=0.10 total=12345
full avg10=0.00 avg60=0.00 avg300=0.00 total=0

PSI 比 load average 好在哪里：

  1. 三个维度独立：CPU、内存、I/O 分开，不会混在一起让你猜瓶颈在哪
  2. 量化的是"等"的比例：some 行表示至少有一个任务在等的 CPU 时间比例，不扩大也不缩小
  3. 区分程度：some 是至少一个任务在等，full 是所有任务都在等——后者严重得多
  4. 有 total 计数器：可以看到从系统启动以来累计的 stall 时间

load average 给的是一个模糊的"系统忙不忙"，PSI 能告诉你"系统在哪个资源上被堵住了、堵了多少"。如果做监控告警，优先看 PSI 而不是 load。

总结 ##

load average 是一个设计巧妙但逐渐跟不上时代的指标：它把 CPU 竞争和 I/O 等待统一抽象为"负载"，简单好用，但 D 状态的计入让它越来越难以精确解读。知道它统计的是 R + D 而不是所有进程，知道 D 状态的真正含义，就能避免很多误判。

实际用的时候，load 高先看 CPU 和 iowait，定位到具体瓶颈；监控体系尽量切换到 PSI，不要再只盯着 load 三个数告警。
