kvm(4)：进程运行时间+CPU占用率，如何更新、计算？

Posted 2026-07-26 21:14 +0800 by ZhangJie ‐ 7 min read

分享:  

写 Split Lock 压垮母机 系列时，总绕不开一个问题：进程的 CPU 时间到底怎么记的。top 里看到的 CPU 使用率、/proc/pid/stat 里的 utime/stime，这些数字是怎么算出来的？内核里其实有两套并行的记账机制，各自基于不同的时间源，在虚拟化场景下可能产生差异。要理解这些，先从内核计时的两个基础概念说起。

一、时钟源：TSC 与 jiffies #

理解记账之前，先搞清楚时间是怎么量的。

TSC（Time Stamp Counter） ##

x86 CPU 内部的 64 位寄存器，从上电复位后按固定频率单调递增。RDTSC 指令读取，用户态可用。

特性说明
精度纳秒级
频率通常等于 CPU 标称频率（2.5GHz = 每秒 +25 亿）
虚拟化KVM 通过 TSC offset 控制 guest 视角：vCPU 运行时 TSC 正常走，deschedule 时"暂停"

jiffies / tick ##

概念含义
tick一次 timer 中断事件
jiffy两次 tick 间的时间间隔，值 =1/HZ 秒
TICK_NSECaccount_process_tick() 每次加给 utime/stime 的时间量，等于 1 jiffy 对应的纳秒数

常见 CONFIG_HZ 下 1 jiffy 的时长：

HZ1 jiffy典型场景
10010ms早期内核
2504msRHEL/CentOS 常见
10001ms桌面、部分服务器

tick 和 jiffy 的关系：每发生 1 次 tick 中断，内核就给当前进程的 utime/stime 累加 1 jiffy 的时长。

有些内核版本是这个配置项: CONFIG_HZ_1000=y，等效于 CONFIG_HZ=1000, 1jiffy=1ms，也就是两个timer tick之间的间隔。

二、两套记账：CFS 时间戳 vs tick 采样 #

在 Linux 2.6.23 引入 CFS 之前，内核完全依赖 timer tick 周期性采样来统计进程 CPU 时间——每次 tick 中断时给 current 加 1/HZ 秒，精度粗糙，无法捕捉不足一个 tick 的短运行。CFS 引入后，新增了基于 TSC 差值的精确统计（update_curr() → sum_exec_runtime），与原有的 tick 统计（account_process_tick() → utime/stime）并行运转至今。

内核里这两套并行的 CPU 时间统计机制，数据来源和用途完全不同。先用一张表建立整体印象：

CFS 统计Tick 统计
数据来源TSC 差值每次 tick 累加固定时长
记录到sum_exec_runtimeutime / stime
精度纳秒级HZ 级（1~10ms）
触发时机每次调度时刻 + tick每次 timer IRQ
丢 tick不会丢时长（TSC 差值照算）少记
补 tick只加实际 TSC 差值（微秒级）oneshot：不多记；periodic：循环多记
用途CFS 调度决策、vruntime/proc/pid/stat、top、times()

两套统计在每次 timer IRQ 里同时运转——update_process_times() 内部，account_process_tick() 和 scheduler_tick()（内含 update_curr()）先后执行，各算各的。

sum_exec_runtime 是进程消耗的物理 CPU 时间，大家常说的 vruntime 就是由它按进程权重（nice 值）折算而来：vruntime += sum_exec_runtime × 1024 / weight。CFS 用 vruntime 做调度决策，本文关注的是物理时间本身，所以讨论的都是 sum_exec_runtime。

下面分别展开。

2.1 CFS 统计：update_curr() → sum_exec_runtime ##

核心函数 update_curr()，触发点远不止 tick：任务切换、入队出队、唤醒抢占、yield 都会走。

static void update_curr(struct cfs_rq *cfs_rq)
{
    struct sched_entity *curr = cfs_rq->curr;
    u64 now = rq_clock_task(rq_of(cfs_rq));
    u64 delta_exec;

    if (unlikely(!curr))
        return;

    delta_exec = now - curr->exec_start;    // TSC 差值，纳秒精度
    if (unlikely((s64)delta_exec <= 0))
        return;

    curr->exec_start = now;
    curr->sum_exec_runtime += delta_exec;   // 精确累计
    curr->vruntime += calc_delta_fair(delta_exec, curr); // 更新调度决策值vruntime
}

每次算的是 rq->clock_task 从上次更新到现在的真实 TSC 增量。tick 丢了？不影响。tick 补了？也不多记。始终跟硬件时间戳走。

2.2 Tick 统计：account_process_tick() → utime / stime ##

两条入口路径，最终都汇入 update_process_times → account_process_tick：

// oneshot 模式
hrtimer_interrupt
  → tick_sched_timer
    → update_process_times
      → account_process_tick

// periodic 模式（循环补 tick）
tick_handle_periodic:
  for each missed tick:           // 对timer IRQ之前每个missed tick都执行tick逻辑
    tick_periodic
      → update_process_times
        → account_process_tick    // 每次加 TICK_NSEC

void account_process_tick(struct task_struct *p, int user_tick)
{
    // HZ=250 时 = 4,000,000 ns = 4ms
    // HZ=1000 时 = 1ms
    u64 cputime = TICK_NSEC;
    // 母机可能不给自己同步 `-cpu host,-kvm-steal-time`
    u64 steal = steal_account_process_time(ULONG_MAX);

    if (steal >= cputime)
        return;

    // 扣除 vCPU 被 host 偷走的时间，避免把没实际运行的时间也算进 utime/stime。
    // 考虑到基于timer tick这种记账方式的缺陷，host同步steal time给guest，理论上应该同步。
    // 否则，比如periodic模式下，可能导致过渡补偿进程运行时间的情况出现 … cpu使用率虚高！
    cputime -= steal;

    if (user_tick)
        account_user_time(p, cputime);    // p->utime += cputime
    else if (...)
        account_system_time(p, cputime);  // p->stime += cputime
    else
        account_idle_time(cputime);
}

记给谁、记 user 还是 system，取决于tick 到来那一刻 CPU 在什么上下文。本质是：以 tick 为最小粒度，按"被看到时的上下文"分摊固定时长。

HZ=250 时粒度 4ms，短跑进程可能多记/少记，长期均摊。麻烦的是丢 tick 或集中补 tick——这个后文虚拟化部分详述。

三、内核配置：决定了"tick记账"是否仍生效 #

CONFIG_VIRT_CPU_ACCOUNTING_GEN，这是对 tick 记账影响最大的编译期配置，决定 account_process_tick() 是真实生效还是基本退化为空操作。

3.1 =n：tick 侧存活，legacy 路径 ##

这是线上 5.4 内核的实际配置。 account_process_tick() 每次 tick 真实累加 TICK_NSEC 到 utime/stime。

# 查看当前内核配置
grep CONFIG_VIRT_CPU_ACCOUNTING_GEN /boot/config-$(uname -r)
# 没有输出或 = n → legacy 路径

此时两套账都在真实运转，/proc/pid/stat 的 utime/stime 来自 tick 累计（经 cputime_adjust 对齐，见下一节）。

3.2 =y：vtime 路径，tick 侧退位 ##

utime/stime 的更新推迟到 context switch 边界，通过 vtime_account_user() / vtime_account_system() 在进出用户态/内核态时精确记账。account_process_tick() 基本是空操作。

grep CONFIG_VIRT_CPU_ACCOUNTING_GEN /boot/config-$(uname -r)
# CONFIG_VIRT_CPU_ACCOUNTING_GEN=y

此时 tick 侧的 account_process_tick() 名存实亡，/proc/pid/stat 的 utime/stime 来自 vtime 记账（同样经 cputime_adjust 对齐）。

3.3 这意味着什么 ##

讨论 tick catchup 会不会灌爆 utime/stime 时，先问：

tick 侧还活着吗？

  • CONFIG_VIRT_CPU_ACCOUNTING_GEN=n：活着。tick catchup（periodic 模式）会灌爆。
  • CONFIG_VIRT_CPU_ACCOUNTING_GEN=y：名存实亡。tick catchup 没什么好灌的。

线上 5.4 + =n → tick 侧存活的 legacy 路径。接下来讨论的 cputime_adjust 和 catchup 行为，都以这个场景为前提。

四、cputime_adjust：两本账的对齐 #

/proc/pid/stat 读到 utime/stime 时，内核会经过 cputime_adjust() 对齐。这不是简单的版本差异（“4.x+ 才有”），4.x+ 都有，但不同 config 下走不同代码路径。

4.1 做什么 ##

即：当 tick 累计的 utime+stime 超过了 sum_exec_runtime，按比例缩回到调度器时间。

// 简化示意 — kernel/sched/cputime.c
static void cputime_adjust(struct task_cputime *curr, struct prev_cputime *prev,
                           u64 *ut, u64 *st)
{
    u64 total_tick = curr->utime + curr->stime;   // tick 累计
    u64 total_sched = curr->sum_exec_runtime;      // 调度器精确值

    // tick 累计不能超过真实 CPU 时间
    if (total_tick > total_sched && total_tick > 0) {
        *ut = scale_u64(curr->utime, total_sched, total_tick);
        *st = scale_u64(curr->stime, total_sched, total_tick);
    }
    // ...还有 prev_cputime 的平滑、边界处理
}

正常场景下，tick 累计和 sum_exec_runtime 基本一致，adjust 是微调。tick catchup 把 tick 侧灌爆后，adjust 以调度器时间为锚往回压。

4.2 能解决什么，不能解决什么 ##

场景adjust 效果
正常稳态微调，基本一致
oneshot + timer 补偿（补 1 次 tick）tick 侧无虚涨，不需要 adjust
periodic + tick catchup loop（补 N 次 tick）adjust 读取时以sum_exec_runtime 为锚压回，用户态工具看到的是调整后的值
非 timer IRQ 风暴（网络中断等）adjust 管不到——中断处理时间被 update_curr() 精确计入，是真实的 CPU 消耗

periodic catchup 在几十微秒内连续调用 N 次 account_process_tick()，每次加满 1 个 tick，tick 侧会短暂膨胀。但 cputime_adjust 在读取 /proc/pid/stat 时就会被调用，atop、top 等工具读到的都是调整后的值，不会看到虚高。

五、虚拟化：timer 补偿对两套统计的不同影响 #

vCPU 被 deschedule 再恢复调度后，host 会把 pending 的中断注入 guest。其中影响进程时间统计的是 timer 中断补偿——missed 的 tick 需要在 vCPU 恢复后补上。至于网卡等设备中断的注入，它们在中断上下文中处理，不走 account_process_tick，不影响 utime/stime。

下面看 timer 补偿在两种 tick 模式下分别怎么影响两套统计。

5.1 Oneshot 模式（线上默认，hrtimer_interrupt） ##

// kernel/time/hrtimer.c
static void __hrtimer_run_queues(...) {
    // 只处理到期的 hrtimer，不循环 missed ticks
}

hrtimer_interrupt              ← 一次中断
  → tick_sched_timer
    → tick_sched_handle
      → update_process_times
          ├── account_process_tick()  ← 调一次，只加 1 jiffy
          └── scheduler_tick()
               └── update_curr()      ← TSC 差值，不多加

不管是 KVM 注入的 timer IRQ 还是正常运行中的 timer IRQ，路径完全一样，各运行一次。即使 jiffies 跳了 50 步（vCPU 被偷走 200ms），account_process_tick() 只加 1 jiffy，update_curr() 只加 TSC 差值。

结论：oneshot 模式下，timer IRQ 不会虚涨进程 CPU 时间，两套账的数据都可信。

5.2 Periodic 模式（highres=off nohz=off 强制启用） ##

// kernel/time/tick-common.c
void tick_handle_periodic(struct clock_event_device *dev)
{
    tick_periodic(cpu);

    for (;;) {
        next = ktime_add_ns(next, TICK_NSEC);
        if (!clockevents_program_event(dev, next, false))
            return;        // next 在未来 → 退出循环
        tick_periodic(cpu); // next 已过去 → 继续补
    }
}

每次 tick_periodic 完整走：

tick_periodic
  → do_timer                          // jiffies +1
  → update_process_times
      ├── account_process_tick()      // utime/stime += TICK_NSEC  ← 循环 N 次！
      └── scheduler_tick()
           └── update_curr()          // TSC 差值                  ← 不循环

vCPU 停摆 200ms（HZ=250 时 = 50 个 tick），catchup 循环 50 次：

tick_periodic #1:   sum_exec_runtime += ~2μs    utime += 4ms
tick_periodic #2:   sum_exec_runtime += ~1μs    utime += 4ms
...
tick_periodic #50:  sum_exec_runtime += ~1μs    utime += 4ms
───────────────────────────────────────────────────────────────
合计:               sum_exec_runtime += ~60μs   utime += 200ms

同一 loop 内，两边行为完全不同：

  • update_curr()：每次只算 TSC 真实增量（微秒级），不跟着循环放大
  • account_process_tick()：每次硬加 TICK_NSEC（毫秒级），跟着循环叠加

然后 cputime_adjust 会在读取 /proc/pid/stat 时把 tick 侧压回 sum_exec_runtime 的范围，用户态工具看到的始终是调整后的值。

结论：periodic 模式下，CFS 侧基于 TSC 差值记账，不受循环影响；tick 侧会被灌爆，但经 cputime_adjust 在读取时压回，用户态不会看到虚高。

六、IRQ 时间：被忽略的第三条记账线 #

除了 utime/stime，account_process_tick() 内部还藏了一条硬中断时间记账：

void account_process_tick(struct task_struct *p, int user_tick)
{
    // ...
    if (user_tick)
        account_user_time(p, cputime);
    else if (...)
        account_system_time(p, cputime);
    else
        account_idle_time(cputime);

    irqtime_account_process_tick(p, user_tick, 1);  // ← 这行
}

irqtime_account_process_tick() 把当前 tick 的时间按比例拆分到 /proc/stat 的 irq、softirq 列。atop 能看到 irq 高，不光来自本就不多的 timer IRQ，更多来自网络中断等非 timer IRQ。

七、编码问题：两点采样法引入的时序错位问题 #

总结下，对 split lock 场景而言，CPU% 偏高可能来自以下因素叠加：

  1. Split lock 本身占着 CPU 空转 → 锁总线期间 CPU 等内存总线就绪，TSC 照走、update_curr() 照记，是真实的 CPU 消耗。原本执行到一定程度就该走网络 IO 切出 CPU，现在占着不走 ;
  2. 大量非 timer IRQ 集中注入（网卡等中断） → 中断处理消耗真实 CPU 时间 → update_curr() 精确计入 sum_exec_runtime → 进一步拉高 CPU% ;
  3. Periodic 模式 timer 补偿循环 → vCPU 恢复后 tick_handle_periodic 循环补 N 次 tick，每次调用 account_process_tick() 加满 TICK_NSEC——循环本身放大了 tick 侧的增量（cputime_adjust 读取时以 sum_exec_runtime 为锚修正）;
  4. Steal time 未同步 → 叠加第 3 条，每次循环没有 steal time 扣除，utime/stime 全额累加 ;

以上因素只能解释 CPU% 偏高，但不能解释 CPU% 超过 100%。因为 cputime_adjust 在每次读取 /proc/pid/stat 时都会以 sum_exec_runtime 为锚修正 utime/stime，如果监控工具的分子和分母取自同一时刻，理论上不会超过 100%。

CPU% >100% ？还有什么其他可能原因？可能要看看编码层面，或者使用的gopsutil库层面。

“两点采样法”时序错位问题：

  1. 监控工具先取了分母（如wallclock差值），now.Sub(prevSampleTime)；
  2. 之后 vCPU 恢复、timer 补偿触发、进程执行继续累加utime/stime，再取读取 /proc/pid/stat计算分子stime+utime-stealtime；

注意：分子已经对应的是更靠后的时间点，会导致CPU使用率虚高，甚至超过100%。这个很好理解，对吧！

解决办法就是计算分子、分母的数据必须要对齐，比如t1、t2两个时间点采集的数据，t1{stime,utime,stealtime,wallclock}, t2{stime,utime,stealtime,wallclock}，尽管采集时这几个数据项也是从不同数据源读取的，但是几乎是同一时刻获取的，误差相对小。我们这么实现的cpumon，就注意了这里的问题，计算结果没有出现明显虚高的情况。

如果是先获取分母，做了一堆逻辑之后，才去获取获取分子，会导致偏大；或者反过来，导致偏小。

八、gopsutil库：存在上述编码问题吗？ #

gopsutil库，编码上来看，也不存在上述问题，我们用的版本是 github.com/shirou/gopsutil/v4 v4.25.2，但是我确实用一种诡异的方式复现了上述问题。我发现采样窗口大小，会影响到这里的测试结果。

// Take process CPU usage within following window size (duration)
procCPU, err := proc.PercentWithContext(ctx, *winsize)
if err != nil {
	log.Printf("Process PID %d no longer accessible: %v", targetPID, err)
	break
}

// Per-core average: this is the key metric
// gopsutil Percent() returns total across all cores, so divide by numCPU
perCore := procCPU / float64(numCPU)

这个可以用几个点来解释：1）分子分母获取存在时间差，不绝对一致；2）读取/proc/pid/stat时内核存在缩放调整；3）读取时存在分子、分母跨越前后两个tick阶段的情况；4）go运行时调度、GC以及vcpu切换等，引入的延迟可能某些情况下比1个tick大 …… 综合多种因素，如果采样窗口小于1tick，那么可能会有较大概率算出CPU使用率虚高的情况。不要使用特别小的采样窗口！

注意：但是，我们线上环境的代码写法，是用的proc.Percent(0)，然后配合1s sleep。效果上基本等同于proc.PercentWithContext(ctx, 1s)。总结下，就是我们还是没有100%复现出线上那样的问题。

总结 #

本文梳理了 Linux 内核中两套并行的进程 CPU 时间统计机制：CFS 侧基于 TSC 差值精确累计到 sum_exec_runtime，tick 侧每 tick 累加固定时长到 utime/stime。介绍了 CONFIG_VIRT_CPU_ACCOUNTING_GEN 如何决定 tick 侧是否真实生效，以及 cputime_adjust 如何在每次读取 /proc/pid/stat 时以 sum_exec_runtime 为锚修正 utime/stime，确保用户态工具读到的始终是正确值。在虚拟化场景中，timer 补偿在 oneshot 和 periodic 两种模式下行为不同，但 cputime_adjust 同样会在读取时兜底。

回到 Split Lock 的原始问题，本文排除了「内核记账机制本身导致 CPU% 虚高到数倍」的可能性。无论 periodic 补偿循环还是 steal time 未同步，都只会让 tick 侧短暂膨胀，cputime_adjust 总能在用户态读取时修正。后面一度怀疑是监控工具两点采样的时序错位导致的，但查看了 gopsutil 库的源码，Percent/PercentWithContext 实现上并不是那种buggy写法。另外，短采样窗口（如 1ms）下确实能打出 >100%，>200% 甚至更高的单核CPU占用率。但是，这主要是记账粒度、缩放与采样宽度不匹配引起，还不能当作线上1s采样窗口达到350% CPU占用率的根因。

在接近线上的配置与写法下，仍未能100%复现单核CPU占用率350%+ —— but，已经了解到的机制可以先写清楚，暂时还没有定论！
